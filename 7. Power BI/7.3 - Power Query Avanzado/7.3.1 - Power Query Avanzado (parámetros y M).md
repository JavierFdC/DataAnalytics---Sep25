## Introducción

En la sesión 7.1.2 construimos un pipeline de limpieza completo para `reservas.csv`. Al final teníamos un Applied Steps bien nombrado, pero con un problema: el pipeline estaba **hardcodeado**. La ruta del archivo, los umbrales de análisis y las reglas de imputación estaban escritos directamente en el código. Si mañana el equipo de IT mueve el CSV a otra carpeta, o si queremos ejecutar el mismo informe para otro año, hay que entrar al Editor y editar código a mano.

Hoy resolvemos eso con dos herramientas que trabajan juntas: los **Query Parameters** (que dan al pipeline puntos de configuración sin tocar código) y el **lenguaje M escrito a mano** (que permite construir transformaciones que la interfaz visual no puede expresar por sí sola).

El hilo conductor de toda la sesión es este: **cada operación la haremos primero desde la interfaz visual, luego veremos el código M que esa interfaz genera, y finalmente aprenderemos a escribir y modificar ese M directamente**. Al terminar, ambas vías serán intercambiables para ti.

### Objetivos de la sesión

- Entender la estructura `let ... in` del lenguaje M y leer cualquier consulta generada por la UI.
- Crear Query Parameters de tipo Texto y Número y conectarlos a la consulta principal.
- Escribir y modificar M en el Advanced Editor para operaciones que la UI no cubre.
- Crear funciones personalizadas en M y aplicarlas a columnas de una tabla.
- Realizar Append y Merge desde la UI y desde M.
- Aplicar gestión de errores con `try ... otherwise` en M.

### Prerequisitos

- `HotelesMediterraneum_7.2.6_resuelto.pbix` con la tabla `reservas` limpia y el modelo de datos completo.
- Dataset `reservas.csv` accesible en la carpeta `7.0 - Dataset`.
- Haber completado la sesión 7.1.2 (Applied Steps, transformación no destructiva).

### 1.2 La estructura `let ... in`

Todo programa M tiene esta forma:

```
let
    Paso1 = <expresión>,
    Paso2 = <expresión que usa Paso1>,
    Paso3 = <expresión que usa Paso2>,
    ...
in
    ÚltimoPaso
```

- **`let`** declara una secuencia de variables con nombre, separadas por comas.
- Cada variable puede usar las variables declaradas antes que ella.
- **`in`** devuelve el valor de lo que le sigue. Eso es el resultado de toda la consulta.
- Los nombres con espacios, tildes o caracteres especiales se escriben entre `#"..."`: `#"Trim channel"`.

El código que ves en el Advanced Editor de tu consulta tiene este aspecto:

```
let
    Origen                  = Csv.Document(File.Contents("C:\...\reservas.csv"), [...]),
    #"Encabezados"          = Table.PromoteHeaders(Origen, [PromoteAllScalars=true]),
    #"Trim channel"         = Table.TransformColumns(#"Encabezados", {{"channel", Text.Trim}}),
    #"Capitalize channel"   = Table.TransformColumns(#"Trim channel", {{"channel", Text.Proper}}),
    ...
    #"Resultado final"      = #"Último paso"
in
    #"Resultado final"
```

Cada línea de este `let` es un paso de Applied Steps. El `in` devuelve el último paso.

### 1.3 Por qué importa leer M aunque uses la UI

A partir de ahora, cada vez que hagas una transformación desde la interfaz, abre el Advanced Editor y lee la línea de M que se acaba de añadir. Este hábito —conectar "clic en botón → expresión M generada"— convierte a un usuario de UI en alguien que entiende lo que está construyendo. En las secciones siguientes lo practicaremos con cada operación.

## 2. Los tres tipos de datos compuestos de M

Antes de parametrizar necesitamos reconocer los tres tipos de datos que aparecen constantemente en el código M generado por la UI. No hace falta memorizarlos ahora: los irás viendo en los ejemplos de cada sección.

### List — lista de valores `{ }`

Una secuencia ordenada, delimitada por llaves:

```
{ "Direct", "Booking", "Expedia", "Agency", "Corporate" }
{ 1, 2, 3 }
```

Aparece, por ejemplo, en `Table.TransformColumns` para indicar qué columnas transformar, o en `Table.SelectColumns` para indicar qué columnas conservar.

### Record — conjunto de campos con nombre `[ ]`

Un conjunto de pares clave-valor, delimitado por corchetes:

```
[Delimiter=",", Columns=15, Encoding=65001]
```

Aparece en los parámetros opcionales de funciones como `Csv.Document` o `Table.PromoteHeaders`. Cuando ves un segundo argumento entre corchetes en el código M generado, es un Record.

### Table — tabla

Es el tipo de retorno principal de casi todas las transformaciones. No se suele construir a mano: se obtiene de `Csv.Document`, `Excel.Workbook`, `Table.Combine`, etc.

## 3. Query Parameters: puntos de configuración sin tocar código

Un Query Parameter es una variable de nivel de modelo que puede ser referenciada desde cualquier consulta. Se define una vez, se usa en cualquier parte, y cambiar su valor actualiza automáticamente todas las consultas que lo usan.

### 3.1 Crear el parámetro de ruta de archivo

#### Desde la UI

En el Editor de Power Query: **Home > Manage Parameters > New Parameter**.

Rellenamos el diálogo:

| Campo | Valor a introducir |
|---|---|
| Name | `RutaDataset` |
| Description | Ruta a la carpeta del dataset de HotelesMediterraneum |
| Required | marcado |
| Type | Text |
| Suggested Values | Any value |
| Current Value | la ruta completa a tu carpeta `7.0 - Dataset` |

Pulsamos **OK**.

> [CAPTURA 3.1 — Diálogo "New Parameter" con los campos Name=RutaDataset, Type=Text y Current Value con una ruta real. Señalar el campo Required marcado.]

#### El código M equivalente

Un parámetro no tiene código M en el Advanced Editor de la consulta principal. Se crea como una **consulta separada** cuyo resultado es un valor escalar. Si abres el panel de consultas (izquierda del Editor) verás que `RutaDataset` aparece ahí como una consulta independiente. Su Advanced Editor contiene simplemente:

```
"C:\ruta\a\tu\carpeta\7.0 - Dataset" meta [IsParameterQuery=true, Type="Text", IsParameterQueryRequired=true]
```

La parte `meta [...]` es metadata que Power Query usa internamente para identificarlo como parámetro. Lo importante para nosotros es la cadena de texto del principio: eso es el valor.

### 3.2 Crear los parámetros de análisis

Repetimos el proceso (**Home > Manage Parameters > New Parameter**) para dos parámetros más:

**Parámetro de año:**

| Campo | Valor |
|---|---|
| Name | `AñoAnalisis` |
| Type | Whole Number |
| Current Value | `2024` |

**Parámetro de umbral de outliers:**

| Campo | Valor |
|---|---|
| Name | `UmbralRevenueOutlier` |

| Current Value | `5000` |

### 3.3 Conectar `RutaDataset` a la consulta de reservas

#### Desde la UI

En el Editor, con la consulta `reservas` activa, hacemos clic en el paso **Source** en el panel Applied Steps. En la barra de fórmulas veremos la expresión M de ese paso. Hacemos clic en el icono de engranaje (⚙) junto al nombre del paso para abrir el diálogo de configuración del origen.

En el diálogo de origen, cambiamos la ruta del archivo. En lugar de escribir la ruta a mano, hacemos clic en el desplegable del campo de ruta y seleccionamos **Parameter > RutaDataset**. Power Query combinará automáticamente el parámetro con el nombre del archivo.

> [CAPTURA 3.3 — Diálogo de configuración del paso Source con el campo de ruta mostrando el parámetro RutaDataset seleccionado en el desplegable.]

#### El código M equivalente

Abrimos el Advanced Editor de la consulta `reservas`. La línea del paso `Origen` pasa de:

```
// Antes: ruta hardcodeada
Origen = Csv.Document(
    File.Contents("C:\ruta\hardcodeada\reservas.csv"),
    [Delimiter=",", Columns=15, Encoding=65001, QuoteStyle=QuoteStyle.None]
),
```

A:

```
// Después: ruta parametrizada
Origen = Csv.Document(
    File.Contents(RutaDataset & "\reservas.csv"),
    [Delimiter=",", Columns=15, Encoding=65001, QuoteStyle=QuoteStyle.None]
),
```

El operador `&` concatena texto en M. `RutaDataset` es la variable que contiene el valor del parámetro. Ahora la ruta completa se construye dinámicamente cada vez que la consulta se ejecuta.

Si el diálogo de UI no permite seleccionar el parámetro directamente (ocurre en algunas versiones de Power BI Desktop con el tipo de conector CSV), la edición directa en el Advanced Editor es la única opción. Por eso es importante saber escribir M además de usar la UI.

### 3.4 Usar `UmbralRevenueOutlier` en la columna de flag

En la sesión 7.1.2 añadimos la columna `revenue_flag` con el umbral de 5.000 hardcodeado.

#### Desde la UI

No existe una opción de la UI para conectar un parámetro a una Conditional Column ya creada. Podemos eliminar el paso existente y recrear la columna condicional desde **Add Column > Conditional Column**, pero el diálogo solo permite valores literales, no parámetros.

**Este es el primer caso donde la UI tiene un límite real**: para usar el parámetro en este cálculo, necesitamos editar M directamente.

#### El código M equivalente

En el Advanced Editor, localizamos el paso de la columna `revenue_flag` y reemplazamos el literal por el parámetro:

```
// Antes
#"Revenue flag" = Table.AddColumn(
    paso_anterior,
    "revenue_flag",
    each if [revenue] > 5000 then "Revisar" else "OK"
),

// Después
#"Revenue flag" = Table.AddColumn(
    paso_anterior,
    "revenue_flag",
    each if [revenue] > UmbralRevenueOutlier then "Revisar" else "OK",
    type text
),
```

Nota el cuarto argumento `type text`: es el tipo de datos de la nueva columna. La UI no lo añade siempre, pero escribirlo evita que Power Query genere un paso automático de cambio de tipo al final.

## 4. Filtrar filas por el parámetro de año

### Desde la UI

Con la consulta `reservas` activa, hacemos clic en el desplegable de la columna `checkin_date`. Seleccionamos **Date Filters > Year > Equals**. En el diálogo introducimos `2024`.

> [CAPTURA 4.1 — Desplegable de filtro de la columna checkin_date con el submenú Date Filters > Year visible.]

El problema: el valor `2024` queda hardcodeado en el paso. Si el año cambia, hay que editar el filtro manualmente.

### El código M equivalente

El paso generado por la UI es:

```
#"Filtro año" = Table.SelectRows(
    paso_anterior,
    each Date.Year([checkin_date]) = 2024
),
```

Para conectarlo al parámetro, editamos esa línea en el Advanced Editor:

```
#"Filtro año" = Table.SelectRows(
    paso_anterior,
    each Date.Year([checkin_date]) = AñoAnalisis
),
```

La palabra clave `each` crea una función anónima implícita donde `_` representa la fila actual. `[checkin_date]` accede al campo de esa fila. Es el equivalente a `lambda row: row["checkin_date"]` en Python.

Ahora cambiar el valor de `AñoAnalisis` en Manage Parameters filtra a un año distinto sin tocar más código.

## 5. Seleccionar y reordenar columnas

### Desde la UI

Para conservar solo un subconjunto de columnas en un orden determinado, seleccionamos con **Ctrl+clic** las columnas que queremos eliminar y usamos **Home > Remove Columns**. Alternativamente, seleccionamos solo las columnas que queremos conservar y usamos **Home > Remove Other Columns**.

Para reordenar: arrastramos las cabeceras de columna a la posición deseada.

### El código M equivalente

Ambas operaciones tienen una función M más directa que lo generado por la UI. En lugar de "eliminar las que sobran" (lo que genera la UI), es mejor práctica "declarar explícitamente las que queremos":

```
#"Columnas seleccionadas" = Table.SelectColumns(
    paso_anterior,
    {
        "reservation_id", "booking_date", "checkin_date", "checkout_date",
        "hotel_id", "channel", "room_type", "nights", "revenue",
        "meal_plan", "status", "is_cancelled", "customer_email", "revenue_flag"
    }
),
```

`Table.SelectColumns` conserva las columnas listadas **en el orden en que las listas**. Si el origen añade columnas nuevas en el futuro, no se propagarán silenciosamente al modelo porque no están en la lista. Es el equivalente a un `SELECT col1, col2, ...` explícito en SQL, y es buena práctica terminar todo pipeline con este paso.

La UI genera `Table.RemoveColumns` (enumera las que elimina). La diferencia es sutil pero importante: si mañana el CSV añade una columna nueva, `Table.RemoveColumns` la dejará pasar al modelo sin avisar, mientras que `Table.SelectColumns` la ignorará.

## 6. Renombrar múltiples columnas

### Desde la UI

La UI solo permite renombrar una columna a la vez: doble clic en la cabecera o **Transform > Rename**. Cada renombrado genera un paso separado en Applied Steps.

### El código M equivalente

En M podemos renombrar todas las columnas que necesitemos en una sola operación:

```
#"Columnas renombradas" = Table.RenameColumns(
    paso_anterior,
    {
        {"booking_date",  "fecha_reserva"},
        {"checkin_date",  "fecha_entrada"},
        {"checkout_date", "fecha_salida"},
        {"hotel_id",      "id_hotel"}
    }
),
```

Un solo paso en Applied Steps en lugar de cuatro. Cuando necesites renombrar más de dos o tres columnas, editar directamente en M es más eficiente y produce un pipeline más limpio que los renombrados individuales de la UI.

## 7. Funciones personalizadas en M

Una función es el mecanismo para encapsular lógica reutilizable. Cuando la misma transformación hay que aplicarla a múltiples columnas o múltiples consultas, convertirla en función elimina la duplicación.

La UI no tiene una opción directa para "crear una función". Este es un caso donde M es la única vía.

### 7.1 Anatomía de una función en M

```
(argumento1 as tipo, argumento2 as tipo) as tipo_retorno =>
    cuerpo de la función
```

El tipo de retorno es opcional. El cuerpo puede ser una expresión simple o un bloque `let ... in` completo.

### 7.2 Crear `fnNormalizarTexto`

En el Editor de Power Query: clic derecho en el panel de consultas (izquierda) > **New Query > Blank Query**. Se abre el Advanced Editor vacío.

Escribimos:

```
let
    fnNormalizarTexto = (texto as text) as text =>
        let
            sinEspacios  = Text.Trim(texto),
            capitalizado = Text.Proper(sinEspacios)
        in
            capitalizado
in
    fnNormalizarTexto
```

Hacemos doble clic sobre el nombre de la consulta en el panel izquierdo y la renombramos `fnNormalizarTexto`.

> [CAPTURA 7.1 — Panel de consultas izquierdo mostrando la consulta fnNormalizarTexto con el icono de función (fx). En el área principal, el Advanced Editor con el código de la función.]

La consulta tipo función aparece en el panel con el icono `fx` en lugar del icono de tabla. Power Query sabe que es una función porque su consulta devuelve una función M, no una tabla.

### 7.3 Aplicar `fnNormalizarTexto` a la tabla

#### Desde la UI

Cuando una función existe en el panel de consultas, podemos invocarla desde la UI: con la consulta `reservas` activa, vamos a **Add Column > Invoke Custom Function**. Seleccionamos `fnNormalizarTexto` y elegimos la columna de entrada.

Este método crea una columna nueva (no transforma la existente), así que después habría que eliminar la original y renombrar. Es útil para funciones que producen resultados complejos; para normalización simple de texto es más directo editar M.

#### El código M equivalente

En el Advanced Editor de `reservas`, localizamos los pasos de Trim y Capitalize de la columna `channel` y los reemplazamos por:

```
#"Texto normalizado" = Table.TransformColumns(
    paso_anterior,
    {
        {"channel",   fnNormalizarTexto, type text},
        {"room_type", fnNormalizarTexto, type text}
    }
),
```

`Table.TransformColumns` recibe una lista de ternas `{nombre_columna, función_a_aplicar, tipo_resultado}`. Aplica la función a cada valor de la columna y opcionalmente fuerza el tipo. Dos columnas normalizadas en un solo paso en lugar de cuatro pasos separados.

### 7.4 Crear `fnParsearFecha` con gestión de errores

En la sesión 7.1.2, la lógica de parseo de fechas se repetía tres veces (para `booking_date`, `checkin_date` y `checkout_date`). Extraigámosla como función.

Nueva Blank Query. Advanced Editor:

```
let
    fnParsearFecha = (textoFecha as text) as nullable date =>
        let
            formato = if Text.Contains(textoFecha, "/")
                      then "dd/MM/yyyy"
                      else if Text.Length(textoFecha) <= 7
                      then null
                      else "yyyy-MM-dd",

            resultado = try (
                if formato = null
                then
                    let
                        partes = Text.Split(textoFecha, "-"),
                        dia    = Text.PadStart(partes{0}, 2, "0"),
                        mes    = Text.PadStart(partes{1}, 2, "0"),
                        anio   = "20" & partes{2},
                        iso    = dia & "-" & mes & "-" & anio
                    in
                        Date.FromText(iso, [Format="dd-MM-yyyy"])
                else
                    Date.FromText(textoFecha, [Format=formato])
            ) otherwise null
        in
            resultado
in
    fnParsearFecha
```

Dos detalles importantes de esta función:

**`nullable date`** como tipo de retorno: la función puede devolver una fecha o `null`. Sin este modificador, M emitiría un error de tipo si `otherwise null` se activa.

**`try ... otherwise null`**: si el parseo falla por cualquier razón (formato no contemplado, carácter inesperado), la función devuelve `null` en lugar de propagar un error a la tabla. El resultado es auditable: podemos contar cuántos nulos hay en las columnas de fecha tras el parseo y decidir si investigar.

Renombramos la consulta `fnParsearFecha`.

#### Comparativa UI vs. M para el parseo de fechas

| | UI (Column from Examples) | M (fnParsearFecha) |
|---|---|---|
| Velocidad de creación | Muy rápida | Requiere escribir código |
| Transparencia de la lógica | Opaca (Power Query infiere) | Explícita y documentada |
| Comportamiento ante formato nuevo | Puede fallar silenciosamente | Devuelve `null` (controlado) |
| Reutilización en otras columnas | Hay que repetir el proceso | Una línea por columna |
| Mantenimiento futuro | Hay que reentrenar el ejemplo | Editar la función en un sitio |

**Cuándo usar cada enfoque:** Column from Examples para exploración rápida o cuando el origen es estable. `fnParsearFecha` cuando el pipeline va a producción o el CSV puede cambiar.

### 7.5 Aplicar `fnParsearFecha` a las tres columnas de fecha

#### Desde la UI

No hay forma directa en la UI de aplicar una función personalizada a varias columnas de fecha en un solo paso. Habría que usar **Invoke Custom Function** tres veces.

#### El código M equivalente

```
#"Fechas parseadas" = Table.TransformColumns(
    paso_anterior,
    {
        {"booking_date",  fnParsearFecha, type date},
        {"checkin_date",  fnParsearFecha, type date},
        {"checkout_date", fnParsearFecha, type date}
    }
),
```

Un paso en lugar de tres bloques de Custom Column. La lógica de parseo vive en un único sitio (`fnParsearFecha`); si la regla cambia, la editamos una sola vez.

> [CAPTURA 7.2 — Applied Steps de reservas mostrando el paso "Fechas parseadas" sustituyendo a los tres bloques de Custom Column originales. En el panel de consultas izquierdo se ven fnNormalizarTexto y fnParsearFecha con icono fx.]

## 8. Append: apilar tablas con el mismo esquema

Append combina dos o más tablas con el mismo esquema apilándolas verticalmente. Es el equivalente a `UNION ALL` en SQL o `pd.concat` en pandas.

**Escenario:** el equipo de HotelesMediterraneum empieza a entregar los datos en dos CSVs semestrales: `reservas_S1.csv` y `reservas_S2.csv`. Queremos una única tabla `reservas` con ambos semestres.

Primero cargamos ambos archivos como consultas separadas (**Get Data > Text/CSV**, dos veces). Los nombramos `reservas_S1` y `reservas_S2`.

### Desde la UI

Con cualquiera de las dos consultas activa: **Home > Append Queries > Append Queries as New**.

En el diálogo seleccionamos las dos consultas y pulsamos **OK**. Se crea una nueva consulta con todas las filas de ambas. La renombramos `reservas`.

> [CAPTURA 8.1 — Diálogo Append Queries con reservas_S1 y reservas_S2 seleccionadas en el panel "Tables to append".]

### El código M equivalente

El paso generado es:

```
#"Reservas combinadas" = Table.Combine({reservas_S1, reservas_S2}),
```

`Table.Combine` recibe una lista de tablas. Podemos añadir más tablas simplemente ampliando la lista:

```
#"Reservas combinadas" = Table.Combine({reservas_S1, reservas_S2, reservas_S3}),
```

**Comportamiento ante esquemas distintos:** si las columnas no coinciden exactamente en nombre, `Table.Combine` rellena con `null` las columnas que faltan en alguna de las tablas. No es un error, es el comportamiento previsto. Si ves nulos inesperados tras un Append, el primer lugar donde mirar es la coherencia de nombres de columna entre los archivos origen.

## 9. Merge: combinar tablas por clave (JOIN)

Merge combina columnas de dos tablas basándose en una columna clave. Es el equivalente a un JOIN relacional.

**Escenario:** tenemos una tabla auxiliar `hoteles.csv` con `hotel_id`, nombre completo, ciudad y categoría de estrellas. Queremos enriquecer `reservas` con esa información.

Primero cargamos `hoteles.csv` como consulta y la nombramos `hoteles`.

### Desde la UI

Con la consulta `reservas` activa: **Home > Merge Queries**.

En el diálogo:
1. Seleccionamos la columna `hotel_id` en `reservas` (clic en su cabecera).
2. En el desplegable de tabla secundaria elegimos `hoteles`.
3. Seleccionamos la columna `hotel_id` en `hoteles`.
4. En **Join Kind** seleccionamos **Left Outer** (conserva todas las filas de `reservas` aunque no haya correspondencia en `hoteles`).

Pulsamos **OK**. Aparece una columna nueva de tipo Table llamada `hoteles`. Hacemos clic en el icono de expansión (↔) en su cabecera, seleccionamos `nombre_hotel`, `ciudad` y `estrellas`, y desmarcamos "Use original column name as prefix".

> [CAPTURA 9.1 — Diálogo Merge Queries configurado: tabla izquierda reservas con hotel_id seleccionado, tabla derecha hoteles con hotel_id seleccionado, Join Kind = Left Outer.]

> [CAPTURA 9.2 — Vista del Editor tras el merge, con la columna "hoteles" de tipo Table visible antes de expandirla. El icono de expansión señalado con una anotación.]

### El código M equivalente

El Merge genera dos pasos en Applied Steps. En M:

```
// Paso 1: el join
#"Merge hoteles" = Table.NestedJoin(
    paso_anterior, {"hotel_id"},
    hoteles,       {"hotel_id"},
    "hoteles",
    JoinKind.LeftOuter
),

// Paso 2: la expansión de columnas
#"Hoteles expandidos" = Table.ExpandTableColumn(
    #"Merge hoteles",
    "hoteles",
    {"nombre_hotel", "ciudad", "estrellas"},
    {"nombre_hotel", "ciudad", "estrellas"}
),
```

Los cuatro argumentos de `Table.ExpandTableColumn` son: la tabla de entrada, el nombre de la columna que contiene la tabla anidada, las columnas a extraer, y los nombres que tendrán en la tabla resultante (útil para renombrar en el mismo paso).

**Tipos de join disponibles:**

| UI | M | Equivalente SQL |
|---|---|---|
| Left Outer | `JoinKind.LeftOuter` | `LEFT JOIN` |
| Right Outer | `JoinKind.RightOuter` | `RIGHT JOIN` |
| Full Outer | `JoinKind.FullOuter` | `FULL OUTER JOIN` |
| Inner | `JoinKind.Inner` | `INNER JOIN` |
| Left Anti | `JoinKind.LeftAnti` | `LEFT JOIN WHERE right IS NULL` |
| Right Anti | `JoinKind.RightAnti` | `RIGHT JOIN WHERE left IS NULL` |

## 10. Pipeline completo: UI vs. M en perspectiva

Llegados a este punto, vale la pena ver el pipeline completo tal como quedaría escrito directamente en M, con los parámetros y funciones conectados. Esto es lo que verías si abrieras el Advanced Editor de la consulta `reservas` al final de la sesión:

```
let
    // === CARGA ===
    Origen = Csv.Document(
        File.Contents(RutaDataset & "\reservas.csv"),
        [Delimiter=",", Columns=15, Encoding=65001, QuoteStyle=QuoteStyle.None]
    ),
    Encabezados = Table.PromoteHeaders(Origen, [PromoteAllScalars=true]),

    // === NORMALIZACIÓN DE TEXTO ===
    TextoNormalizado = Table.TransformColumns(Encabezados, {
        {"channel",   fnNormalizarTexto, type text},
        {"room_type", fnNormalizarTexto, type text}
    }),

    // === CORRECCIONES RESIDUALES DE CHANNEL ===
    ChannelCorregido = Table.ReplaceValue(
        TextoNormalizado, "Booking.Com", "Booking",
        Replacer.ReplaceText, {"channel"}
    ),

    // === PARSEO DE FECHAS ===
    FechasParseadas = Table.TransformColumns(ChannelCorregido, {
        {"booking_date",  fnParsearFecha, type date},
        {"checkin_date",  fnParsearFecha, type date},
        {"checkout_date", fnParsearFecha, type date}
    }),

    // === IMPUTACIÓN DE NULOS ===
    MealPlanImputado = Table.ReplaceValue(
        FechasParseadas, null, "Room Only",
        Replacer.ReplaceValue, {"meal_plan"}
    ),

    // === RECONSTRUCCIÓN DE is_cancelled ===
    SinIsCancelled    = Table.RemoveColumns(MealPlanImputado, {"is_cancelled"}),
    IsCancelledNuevo  = Table.AddColumn(
        SinIsCancelled, "is_cancelled",
        each [status] = "Cancelled",
        type logical
    ),

    // === FILTRO POR AÑO ===
    FiltradoAño = Table.SelectRows(
        IsCancelledNuevo,
        each Date.Year([checkin_date]) = AñoAnalisis
    ),

    // === FLAG DE OUTLIERS ===
    ConFlag = Table.AddColumn(
        FiltradoAño, "revenue_flag",
        each if [revenue] > UmbralRevenueOutlier then "Revisar" else "OK",
        type text
    ),

    // === SELECCIÓN FINAL DE COLUMNAS ===
    Resultado = Table.SelectColumns(ConFlag, {
        "reservation_id", "booking_date", "checkin_date", "checkout_date",
        "hotel_id", "channel", "room_type", "nights", "revenue",
        "meal_plan", "status", "is_cancelled", "customer_email", "revenue_flag"
    })
in
    Resultado
```

Este código es **funcionalmente idéntico** al pipeline construido paso a paso desde la UI. La diferencia está en la legibilidad, la compacidad y la capacidad de usar parámetros y funciones en cualquier punto. Los comentarios (líneas que empiezan con `//`) son válidos en M y no generan pasos en Applied Steps.

> [CAPTURA 10.1 — Advanced Editor mostrando el pipeline completo con los comentarios de sección visibles. Applied Steps en paralelo mostrando los pasos correspondientes.]

## 11. Cuándo usar la UI y cuándo escribir M directamente

Esta es la pregunta práctica que queda después de la sesión. La respuesta no es "uno siempre mejor que otro": son complementarios.

| Situación | Recomendación |
|---|---|
| Exploración inicial, prototipo rápido | UI: más rápida, sin necesidad de recordar sintaxis |
| Conectar parámetros a expresiones | M directo: la UI no siempre lo permite |
| Renombrar más de 2-3 columnas a la vez | M directo: un paso limpio vs. muchos pasos individuales |
| Transformar la misma lógica en múltiples columnas | M con función personalizada |
| Filtros con lógica condicional compleja | M directo: más legible que múltiples Conditional Columns anidadas |
| Append de 2-3 tablas del mismo esquema | UI: rápida y correcta |
| Merge simple con Left Outer | UI: cómoda para elegir columnas a expandir |
| Ajustar un paso generado por la UI (p. ej., añadir el tipo de retorno) | Editar en M el paso existente |
| Documentar la lógica de transformación | M con comentarios `//` en el Advanced Editor |

El flujo habitual de un profesional: construir el esqueleto desde la UI, luego abrir el Advanced Editor para ajustar parámetros, extraer funciones y añadir la capa final de `Table.SelectColumns`.

## 12. Lo que Power Query ha hecho por debajo

Cada paso visible en el panel Applied Steps es una expresión M que Power Query evalúa en orden. La UI no genera código al vuelo cuando pulsas un botón: construye un árbol de expresiones M y lo materializa solo cuando se solicita una vista previa o se ejecuta un refresco. Esto es lo que M llama **evaluación perezosa** (lazy evaluation): las expresiones no se ejecutan hasta que algo las pide.

Cuando haces clic en **Promote Headers**, Power Query añade al árbol la expresión `Table.PromoteHeaders(pasoAnterior, ...)`. El motor no ejecuta esa función en el acto; registra la transformación. Solo cuando pulsas **Refresh Preview** o cuando el refresco del modelo lo requiere, el motor recorre el árbol de arriba abajo y evalúa cada expresión en secuencia.

Los **parámetros** son un caso especial: son consultas M cuyo resultado es un valor escalar. Cuando el motor evalúa `File.Contents(RutaDataset & "\reservas.csv")`, resuelve primero la consulta `RutaDataset` para obtener la cadena de texto, y luego concatena y pasa el resultado a `File.Contents`. La resolución ocurre en cada refresco, no en el momento de crear el parámetro. Si cambias el valor del parámetro y no refrescas, el pipeline sigue usando el valor anterior en caché de la vista previa.

Las **funciones personalizadas** (`fnNormalizarTexto`, `fnParsearFecha`) son también consultas M cuyo resultado es una función. Cuando `Table.TransformColumns` las invoca, el motor sustituye cada llamada por el cuerpo de la función con el argumento concreto. No hay ninguna diferencia de rendimiento respecto a escribir la lógica inline: el motor las expande antes de ejecutar.

El **plegado de consultas** (query folding) entra en juego cuando el origen soporta SQL o algún lenguaje de consulta nativo. En ese caso, Power Query traduce las expresiones M a SQL y delega la ejecución al origen. Los archivos CSV no admiten plegado: todas las transformaciones se ejecutan en memoria en el proceso del gateway o del Desktop. Por eso un CSV de 2 millones de filas carga toda esa masa de datos antes de filtrar; un SQL Server con plegado enviaría `WHERE Date.Year(checkin_date) = 2024` al servidor y solo bajaría las filas del año.

## 13. Errores comunes

**"Al usar el parámetro en File.Contents obtengo error de ruta."**
El valor de `RutaDataset` no debe terminar en `\`. La concatenación `RutaDataset & "\reservas.csv"` ya añade la barra. Si el parámetro termina en `\`, la ruta resultante tendrá `\\` doble y fallará.

**"Table.Combine produce nulos inesperados donde debería haber datos."**
Los nombres de columna no coinciden exactamente entre las tablas origen. Power Query distingue entre `booking_date` y `Booking_Date`. Revisa los encabezados de cada CSV antes de combinar.

**"Al aplicar fnNormalizarTexto sale error de tipo."**
La función espera `text` pero la columna tiene tipo `Any`. Añade un paso de tipado explícito antes: `Table.TransformColumnTypes(paso, {{"channel", type text}})`.

**"La función fnParsearFecha devuelve null en filas que deberían funcionar."**
Para diagnosticar, cambia temporalmente `otherwise null` por `otherwise [HasError=true, Error=error[Message]]`. Esto muestra el mensaje de error en lugar de ocultarlo con null, permitiendo identificar qué formato está fallando.

**"Edité el Advanced Editor y ahora Applied Steps está vacío."**
El código M tiene un error de sintaxis que impide que Power Query lo parsee. El editor muestra el error en la barra inferior. Los errores más comunes son: coma faltante al final de un paso (todos menos el último deben terminar en `,`), uso de `"` en lugar de `#"..."` para nombres con espacios, o paréntesis desbalanceados.

**"Cambiar el valor del parámetro no actualiza la consulta."**
En el Editor de Power Query, hay que pulsar **Refresh Preview** (barra superior) después de cambiar el valor de un parámetro. En el modelo principal usa **Home > Refresh**.

## 14. Ampliación opcional

### Extra 1: Parámetro con lista de valores permitidos

En el diálogo de edición de `AñoAnalisis`, cambiamos **Suggested Values** de "Any value" a "List of values" e introducimos `2022`, `2023`, `2024`. Con esta configuración, el diálogo de Manage Parameters muestra un desplegable en lugar de un campo libre. Útil para evitar que se introduzca un año sin datos.

### Extra 2: Diagnóstico de calidad con `Table.Profile`

M incluye una función que calcula estadísticas de calidad de todas las columnas en una sola operación:

```
let
    Perfil = Table.Profile(reservas)
in
    Perfil
```

#### Desde la UI

No hay equivalente exacto en la UI para obtener esta tabla de estadísticas. El Column Quality y Column Distribution del Editor muestran la misma información visualmente, pero no como tabla exportable. `Table.Profile` en M es la única forma de obtener esos valores como una tabla que podemos consultar o filtrar.

Creamos esta consulta como `DiagnosticoCalidad` y la dejamos sin cargar al modelo (clic derecho sobre la consulta > desmarcar **Enable Load**). Es un recurso de validación disponible durante el desarrollo sin ocupar memoria en el modelo final.

### Extra 3: Tabla de configuración desde Excel

Los parámetros de Power Query tienen un límite: para cambiarlos hay que abrir el Editor de Power Query. En entornos donde el informe lo usan analistas sin acceso al Editor, es más cómodo leer la configuración desde una tabla de Excel.

Creamos una pestaña `Config` en un Excel con dos columnas: `Parametro` y `Valor`. Una fila por parámetro.

En una nueva Blank Query, cargamos ese Excel y convertimos la tabla en un Record para acceder a los valores por nombre:

```
let
    Libro        = Excel.Workbook(File.Contents(RutaDataset & "\config.xlsx")),
    TablaConfig  = Libro{[Name="Config"]}[Data],
    ConEncabezado = Table.PromoteHeaders(TablaConfig, [PromoteAllScalars=true]),

    ConfigRecord = Record.FromList(
        Table.Column(ConEncabezado, "Valor"),
        Table.Column(ConEncabezado, "Parametro")
    )
in
    ConfigRecord
```

Luego en la consulta `reservas` usamos `ConfigRecord[AñoAnalisis]` en lugar del parámetro nativo de Power Query.

#### Desde la UI

No hay equivalente en la UI para este patrón. Es un caso donde M es imprescindible. La UI puede cargar el Excel, pero transformar la tabla de dos columnas en un Record con acceso por nombre requiere editar el Advanced Editor directamente.
