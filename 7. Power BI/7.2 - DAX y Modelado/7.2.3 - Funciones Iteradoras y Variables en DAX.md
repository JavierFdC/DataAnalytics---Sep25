## 1. Las funciones X — el modelo de dos fases

### ¿Qué es un iterador en DAX?

En DAX, los iteradores son funciones que procesan una tabla **fila a fila** antes de agregar el resultado. Su nombre siempre termina en `X`: `SUMX`, `AVERAGEX`, `MAXX`, `MINX`, `COUNTX`, `RANKX`.

El proceso ocurre en dos fases:

```
Fase 1 — ITERACIÓN:   Para cada fila de la tabla → evalúa la expresión
Fase 2 — AGREGACIÓN:  Combina todos los resultados (suma, promedio, máximo...)
```

Compara con una función simple:

| Función | Proceso | Cuándo usarla |
|---|---|---|
| `SUM(reservas[revenue])` | Suma la columna directamente | Cuando la columna ya contiene el valor final |
| `SUMX(reservas, expresión)` | Evalúa fila a fila, luego suma | Cuando necesitas calcular algo por fila primero |
| `AVERAGE(reservas[revenue])` | Promedio de la columna directamente | Promedio simple de un campo existente |
| `AVERAGEX(reservas, expresión)` | Promedio de un valor calculado por fila | Cuando el promedio requiere lógica por fila |

### Sintaxis general

```
FUNCIÓN_X( <tabla>, <expresión> )
```

- **tabla**: qué filas iterar. Puede ser toda la tabla o el resultado de `FILTER`.
- **expresión**: qué calcular en cada fila. Aquí puedes usar columnas de esa tabla directamente porque estás en *contexto de fila*.

### Contexto de fila dentro del iterador

Dentro de la expresión de un iterador, DAX establece un **contexto de fila** para cada fila procesada. Esto significa que puedes referenciar `reservas[nights]` o `reservas[revenue]` y obtendrás el valor de esa fila específica, no un agregado.

```
SUMX(
    reservas,
    reservas[revenue] * 0.1   -- 'revenue' aquí = el revenue de ESA fila
)
```

> Diferencia clave: fuera de un iterador, escribir `reservas[revenue]` en una medida sin contexto de fila provoca un error. Dentro de `SUMX`, `AVERAGEX`, etc., DAX ya tiene la fila activa y funciona correctamente.

## 2. SUMX — Sumas con lógica por fila

### Sintaxis

```
SUMX( <tabla>, <expresión> )
```

### Cuándo SUMX y cuándo SUM

`SUM(reservas[revenue])` y `SUMX(reservas, reservas[revenue])` producen **exactamente el mismo resultado**. Si solo estás sumando una columna existente, usa `SUM`: es más rápido y más legible.

`SUMX` es imprescindible cuando la expresión que quieres sumar no existe como columna, sino que resulta de una operación por fila.

### Ejemplo clave: Revenue de reservas confirmadas con lógica condicional

En 7.2.1 usamos `CALCULATE(..., reservas[status] = "Confirmed")` para filtrar. Con `SUMX` podemos hacer lo mismo con lógica condicional explícita por fila:

```
[Revenue Confirmado SUMX] =
SUMX(
    reservas,
    IF( reservas[status] = "Confirmed", reservas[revenue], 0 )
)
```

Esto es equivalente a:

```
[Revenue Confirmado CALCULATE] =
CALCULATE( [Revenue Total], reservas[status] = "Confirmed" )
```

> Ambas opciones son correctas. `CALCULATE` es generalmente más eficiente. `SUMX` con `IF` es útil cuando la condición afecta el *valor* (no solo si se incluye la fila), por ejemplo aplicando descuentos o penalizaciones por fila.

### Medida práctica: Revenue ponderado por adultos

¿Cuánto revenue genera en total cada plaza de adulto en el hotel?

```
[Revenue por Plaza Adulto Total] =
SUMX(
    reservas,
    DIVIDE( reservas[revenue], reservas[adults] )
)
```

Esta medida divide el revenue de cada reserva entre el número de adultos de esa reserva, luego suma. El resultado es distinto a `DIVIDE([Revenue Total], SUM(reservas[adults]))` porque este último pondera diferente (no divide fila a fila).

### Medida práctica: Noches de reservas con pension completa

```
[Noches All Inclusive] =
SUMX(
    reservas,
    IF( reservas[meal_plan] = "All Inclusive", reservas[nights], 0 )
)
```

## 3. AVERAGEX — Promedios calculados por fila

### Sintaxis

```
AVERAGEX( <tabla>, <expresión> )
```

### La diferencia crítica respecto a AVERAGE

Esta es la distinción más importante de la sesión y merece un ejemplo detallado.

Imagina tres reservas:

| booking_id | revenue | nights | revenue / night |
|---|---|---|---|
| B001 | 300 | 3 | 100 |
| B002 | 800 | 2 | 400 |
| B003 | 150 | 5 | 30 |
| **Total** | **1.250** | **10** | — |

**`[ADR]` global** = `DIVIDE([Revenue Total], [Noches Vendidas])` = 1.250 / 10 = **125 €/noche**

**`[ADR por Reserva]`** = `AVERAGEX(reservas, DIVIDE(reservas[revenue], reservas[nights]))` = (100 + 400 + 30) / 3 = **176,7 €/noche**

La diferencia existe porque `[ADR]` pondera las noches (las reservas largas tienen más peso) mientras que `[ADR por Reserva]` pondera las reservas (cada reserva cuenta igual).

Ambas son métricas válidas con interpretaciones distintas. `[ADR por Reserva]` es útil para entender qué paga *un cliente típico* por noche, independientemente de cuántos días se quede.

### Medida: ADR por Reserva

```
[ADR por Reserva] =
AVERAGEX(
    reservas,
    DIVIDE( reservas[revenue], reservas[nights] )
)
```

### Medida: Lead Time Promedio

El *lead time* es el número de días entre que el cliente hace la reserva y la fecha de checkin. No existe como columna en el dataset, pero podemos calcularlo fila a fila:

```
[Lead Time Promedio] =
AVERAGEX(
    reservas,
    DATEDIFF( reservas[booking_date], reservas[checkin_date], DAY )
)
```

> `DATEDIFF` devuelve un entero: los días entre la fecha de reserva y la de llegada. Si `booking_date` es posterior a `checkin_date` (dato erróneo), devuelve un número negativo. Considera añadir `MAX(0, ...)` si el dataset tiene inconsistencias.

Esta medida es especialmente útil segmentada por canal: los canales directos suelen tener lead time más corto que las OTAs.

### Medida: Noches Promedio por Reserva

```
[Noches Promedio] =
AVERAGEX(
    reservas,
    reservas[nights]
)
```

> `AVERAGEX(reservas, reservas[nights])` es equivalente a `AVERAGE(reservas[nights])`. En este caso `AVERAGE` es preferible por simplicidad. Usamos `AVERAGEX` cuando la expresión no es una columna simple.

## 4. MAXX y MINX — Extremos calculados por fila

### Sintaxis

```
MAXX( <tabla>, <expresión> )
MINX( <tabla>, <expresión> )
```

Devuelven el valor máximo o mínimo de una expresión evaluada fila a fila. Útil cuando el máximo no es de una columna existente sino de algo calculado.

### Medida: Revenue máximo de una sola reserva

```
[Revenue Máximo Reserva] =
MAXX(
    reservas,
    reservas[revenue]
)
```

> Equivalente a `MAX(reservas[revenue])`. Úsalo con `MAXX` cuando la expresión no es una columna directa.

### Medida: Lead Time máximo

```
[Lead Time Máximo] =
MAXX(
    reservas,
    DATEDIFF( reservas[booking_date], reservas[checkin_date], DAY )
)
```

### Medida: ADR más alto de una reserva individual

```
[ADR Máximo por Reserva] =
MAXX(
    reservas,
    DIVIDE( reservas[revenue], reservas[nights] )
)
```

Esta medida muestra el ADR de la reserva más cara por noche, no el ADR promedio del hotel. Es útil para detectar outliers o el techo de precio que acepta el mercado.

### Combinación con FILTER: máximo en confirmadas

```
[Revenue Máximo Confirmada] =
MAXX(
    FILTER( reservas, reservas[status] = "Confirmed" ),
    reservas[revenue]
)
```

## 5. RANKX — Rankings dinámicos

### Sintaxis completa

```
RANKX( <tabla>, <expresión>, [<valor>], [<orden>], [<ties>] )
```

| Parámetro | Descripción | Valores posibles |
|---|---|---|
| `tabla` | El conjunto de entidades a clasificar | Normalmente `ALL(columna)` |
| `expresión` | Qué métrica usar para la clasificación | Una medida o expresión DAX |
| `valor` | Valor a clasificar (opcional) | Si se omite, usa el valor del contexto actual |
| `orden` | Ascendente o descendente | `DESC` (defecto), `ASC` |
| `ties` | Cómo gestionar empates | `SKIP` (defecto), `DENSE` |

### SKIP vs DENSE

| Posiciones | SKIP | DENSE |
|---|---|---|
| Tres hoteles con el mismo revenue | 1, 1, 3 | 1, 1, 2 |
| Uso | Ranking deportivo clásico | Ranking continuo sin huecos |

### Medida: Ranking de hoteles por Revenue Neto

```
[Ranking Hotel por Revenue] =
RANKX(
    ALL( reservas[hotel_name] ),
    [Revenue Neto]
)
```

`ALL(reservas[hotel_name])` es esencial: elimina el filtro sobre `hotel_name` para que el ranking compare *todos* los hoteles aunque el visual esté filtrado por uno solo.

### Medida: Ranking de hoteles por ADR

```
[Ranking Hotel por ADR] =
RANKX(
    ALL( reservas[hotel_name] ),
    [ADR]
)
```

### Medida: Ranking de canales por número de reservas

```
[Ranking Canal por Reservas] =
RANKX(
    ALL( reservas[channel] ),
    [Reservas Totales]
)
```

### Medida: Flag Top 3 hoteles

Para destacar visualmente los tres hoteles con más revenue:

```
[Es Top 3 Revenue] =
IF(
    [Ranking Hotel por Revenue] <= 3,
    "Top 3",
    "Resto"
)
```

> Esta medida devuelve texto, no un número, así que no puede usarse en agregaciones. Úsala en formato condicional de tablas o matrices para colorear las filas de los hoteles líderes.

### RANKX con orden ascendente: ranking de cancelaciones

El primer puesto en cancelaciones lo queremos para el hotel con *más* cancelaciones, lo que paradójicamente es el peor resultado. Si usas `RANKX` con `ASC`, el hotel con *menor* cancellation rate ocupa el puesto 1 (mejor):

```
[Ranking Hotel Menor Cancelación] =
RANKX(
    ALL( reservas[hotel_name] ),
    [Cancellation Rate],
    ,
    ASC
)
```

> Los parámetros opcionales `valor` y `orden` se separan por comas. Si omites `valor` pero quieres especificar `orden`, deja el tercer argumento vacío: `RANKX(ALL(...), [medida], , ASC)`.

## 6. Variables avanzadas: VAR / RETURN

### Repaso: la estructura básica

Ya usamos `VAR` / `RETURN` en 7.2.2 para las medidas YoY. Aquí profundizamos en tres patrones avanzados.

### Patrón 1: Variables múltiples y reutilización

```
[Análisis Revenue Reserva] =
VAR _revenue_total     = [Revenue Neto]
VAR _reservas_totales  = [Reservas Totales]
VAR _revenue_promedio  = DIVIDE( _revenue_total, _reservas_totales )
VAR _adr_por_reserva   = [ADR por Reserva]
RETURN
    DIVIDE( _revenue_promedio, _adr_por_reserva )
```

Las variables pueden referenciarse entre sí: `_revenue_promedio` usa `_revenue_total` y `_reservas_totales`, que ya están calculadas. El orden de declaración importa: solo puedes usar una variable *después* de haberla declarado.

### Patrón 2: VAR dentro de iteradores

Puedes declarar variables dentro de la expresión de un iterador para hacer el código más legible:

```
[Revenue Ajustado por Estancia] =
SUMX(
    reservas,
    VAR _revenue  = reservas[revenue]
    VAR _noches   = reservas[nights]
    VAR _tarifa_noche = DIVIDE( _revenue, _noches )
    RETURN
        IF( _noches >= 3, _tarifa_noche * _noches * 0.95, _revenue )
)
```

Esta medida aplica un descuento del 5% en la tarifa a reservas de 3 o más noches, recalculando el revenue total. Sin variables, la fórmula sería ilegible.

### Patrón 3: VAR para evitar evaluaciones repetidas

```
[Revenue YoY % Optimizado] =
VAR _actual   = [Revenue Neto]
VAR _anterior = CALCULATE( [Revenue Neto], SAMEPERIODLASTYEAR( Calendario[Fecha] ) )
RETURN
    IF(
        NOT ISBLANK( _anterior ),
        DIVIDE( _actual - _anterior, _anterior ),
        BLANK()
    )
```

> `[Revenue Neto]` y `CALCULATE([Revenue Neto], SAMEPERIODLASTYEAR(...))` son evaluaciones costosas. Al guardarlas en variables, se calculan *una vez*. El `RETURN` solo opera sobre los valores ya calculados, sin re-evaluar nada.

### Cuándo NO usar VAR

- **Variables de tabla**: `VAR _tabla = FILTER(reservas, ...)` es válido, pero si la tabla resultante es muy grande puede consumir mucha memoria. En esos casos considera si `CALCULATE` con filtros es más eficiente.
- **Variables estáticas**: DAX evalúa las variables en el contexto en que se declaran. Si necesitas que el contexto cambie dentro del cálculo, usa directamente la función en lugar de una variable.

### Ejercicio 2 — Intermedio
Crea `[Lead Time Promedio Canal Directo]` que calcule el lead time promedio *solo* para reservas del canal "Direct":

```
[Lead Time Promedio Canal Directo] =
AVERAGEX(
    FILTER( reservas, reservas[channel] = "Direct" ),
    DATEDIFF( reservas[booking_date], reservas[checkin_date], DAY )
)
```

Compara este valor con `[Lead Time Promedio]` general. ¿Las reservas directas se hacen con más o menos antelación?

### Ejercicio 3 — Avanzado
Crea la medida `[Revenue Top 5 Hoteles]` que sume el revenue solo de los 5 hoteles con mayor revenue:

```
[Revenue Top 5 Hoteles] =
SUMX(
    TOPN(
        5,
        ALL( reservas[hotel_name] ),
        [Revenue Neto],
        DESC
    ),
    [Revenue Neto]
)
```

> `TOPN(n, tabla, expresión, orden)` devuelve una tabla con las n filas superiores según la expresión. Aquí se combina con `SUMX` para sumar el revenue de esos 5 hoteles. `ALL(reservas[hotel_name])` garantiza que el top 5 se calcula sobre todos los hoteles, sin importar el filtro del visual.

Crea también la medida `[% Revenue Top 5]` = `DIVIDE([Revenue Top 5 Hoteles], [Revenue Neto])`. ¿Qué porcentaje del revenue total concentran los 5 hoteles líderes?

### Ejercicio 4 — Reto
Crea un ranking de *tipos de habitación* por **diferencia entre ADR por Reserva y ADR global**. El tipo de habitación con mayor diferencia positiva es el que más se beneficia de reservas cortas de alta tarifa. Usa `RANKX` con `ALL(reservas[room_type])` y como métrica `[ADR por Reserva] - [ADR]`.

## 10. Errores comunes y soluciones

| Error | Causa probable | Solución |
|---|---|---|
| *"A single value for column cannot be determined"* | Referencia a una columna de tabla fuera de contexto de fila | Envolver la referencia dentro de un iterador o usar `MAX()` / `MIN()` |
| `[Ranking Hotel por Revenue]` devuelve el mismo valor para todos | `ALL()` omitido en el primer argumento de `RANKX` | Usar `ALL(reservas[hotel_name])` en lugar de `reservas` |
| `AVERAGEX` devuelve error cuando `nights` = 0 | División por cero en `DIVIDE(revenue, nights)` | Usar `DIVIDE(reservas[revenue], reservas[nights])` en lugar del operador `/`; `DIVIDE` devuelve `BLANK()` en lugar de error |
| `VAR` dentro de iterador no toma el contexto de fila | Variable declarada fuera del iterador pero usada dentro | Declarar la `VAR` *dentro* de la expresión del iterador |
| `RANKX` con `DENSE` no muestra el valor esperado en empates | El tercer parámetro `valor` no se omite correctamente | Comprobar la sintaxis: `RANKX(ALL(...), [medida], , DESC, DENSE)` |
| `[Es Top 3 Revenue]` aparece en blanco en el visual | La medida devuelve texto y no hay contexto de `hotel_name` | Asegúrate de que el visual tiene `reservas[hotel_name]` en las filas |

## 11. Lo que DAX ha hecho por debajo

**SUMX itera en contexto de fila, no en contexto de filtro**

```
[Revenue por Plaza Adulto Total] =
SUMX(reservas, DIVIDE(reservas[revenue], reservas[adults]))
```

Para cada fila de la tabla `reservas`, DAX establece un contexto de fila: `reservas[revenue]` y `reservas[adults]` tienen el valor de esa fila concreta, no de la tabla completa. `DIVIDE` divide esos dos valores. Luego, cuando termina de recorrer todas las filas, suma todos los resultados. El contexto de filtro del visual (hotel, mes, canal) sigue activo: `SUMX` solo itera las filas que sobreviven a ese filtro.

El equivalente SQL sería:

```sql
SELECT SUM(revenue / NULLIF(adults, 0))
FROM reservas
WHERE hotel = 'Hotel Mediterráneo Málaga';  -- filtro del visual
```

**La diferencia entre contexto de fila y contexto de filtro importa en AVERAGEX**

```
[ADR por Reserva] = AVERAGEX(reservas, DIVIDE(reservas[revenue], reservas[nights]))
```

Dentro del `AVERAGEX`, `reservas[revenue]` y `reservas[nights]` son valores de una fila específica (contexto de fila). Fuera de un iterador, escribir `reservas[revenue]` en una medida sin un contexto de fila activo devuelve error. Los iteradores son el mecanismo que habilita el contexto de fila en DAX.

**VAR evalúa en el momento de su definición, no en el de su uso**

```
[Revenue YoY % Optimizado] =
VAR _actual   = [Revenue Neto]
VAR _anterior = CALCULATE([Revenue Neto], SAMEPERIODLASTYEAR(Calendario[Fecha]))
RETURN
    IF(NOT ISBLANK(_anterior), DIVIDE(_actual - _anterior, _anterior), BLANK())
```

`_actual` se evalúa en el contexto de filtro del momento en que se declara la variable: el contexto del visual (por ejemplo, "Hotel Málaga, junio 2024"). `_anterior` se evalúa en ese mismo momento pero con el contexto modificado por `CALCULATE`. Cuando el `RETURN` usa `_actual` y `_anterior`, sus valores ya están calculados y no se recalculan. Esto es lo que evita evaluar `[Revenue Neto]` dos veces.

**RANKX recalcula la expresión para cada fila de la tabla del primer argumento**

```
[Ranking Hotel por Revenue] = RANKX(ALL(reservas[hotel_name]), [Revenue Neto])
```

`ALL(reservas[hotel_name])` devuelve una tabla con todos los nombres de hotel únicos (sin filtros). `RANKX` evalúa `[Revenue Neto]` una vez para cada hotel de esa lista, usando ese hotel como contexto de filtro. Luego compara el valor del hotel actual (el del contexto del visual) con todos esos valores y devuelve su posición.

## 12. Errores comunes

| Error | Causa probable | Solución |
|---|---|---|
| *"A single value for column cannot be determined"* | Referencia a una columna de tabla fuera de contexto de fila | Envolver la referencia dentro de un iterador o usar `MAX()` / `MIN()` |
| `[Ranking Hotel por Revenue]` devuelve el mismo valor para todos | `ALL()` omitido en el primer argumento de `RANKX` | Usar `ALL(reservas[hotel_name])` en lugar de `reservas` |
| `AVERAGEX` devuelve error cuando `nights` = 0 | División por cero en `DIVIDE(revenue, nights)` | Usar `DIVIDE(reservas[revenue], reservas[nights])` en lugar del operador `/`; `DIVIDE` devuelve `BLANK()` en lugar de error |
| `VAR` dentro de iterador no toma el contexto de fila | Variable declarada fuera del iterador pero usada dentro | Declarar la `VAR` *dentro* de la expresión del iterador |
| `RANKX` con empates no muestra el comportamiento esperado | El quinto parámetro `ties` no se especifica | Comprobar la sintaxis: `RANKX(ALL(...), [medida], , DESC, DENSE)` para ranking continuo sin huecos |
| `[Es Top 3 Revenue]` aparece en blanco en el visual | La medida devuelve texto y no hay contexto de `hotel_name` | Asegúrate de que el visual tiene `reservas[hotel_name]` en las filas |
