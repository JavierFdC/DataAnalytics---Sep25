## Contexto de la sesión

En 7.1.3 creamos la tabla `Calendario` con `CALENDARAUTO()` y la marcamos como Date Table. En 7.2.2 usamos esa tabla para calcular medidas de Time Intelligence. En 7.2.5 añadimos jerarquías temporales.

## 1. CALENDAR() vs CALENDARAUTO(): cuándo usar cada una

### CALENDARAUTO()

`CALENDARAUTO()` escanea todas las columnas de fecha de todas las tablas cargadas en el modelo y genera una tabla con un día por fila cubriendo ese rango automáticamente.

**Ventajas:**
- Sin parámetros: se adapta sola cuando los datos cambian de rango.
- Ideal para proyectos en fase de exploración donde el rango de fechas no está fijado.

**Inconvenientes:**
- Si el modelo incluye tablas con fechas en rangos inesperados (p. ej., una tabla de parámetros con una fecha de 2099), el calendario se extiende innecesariamente hasta esa fecha, añadiendo miles de filas vacías.
- No permite definir el rango de forma explícita y controlada.

### CALENDAR(fecha_inicio, fecha_fin)

`CALENDAR()` genera la misma tabla de una fila por día, pero con el rango que el desarrollador define explícitamente.

```dax
Calendario =
CALENDAR( DATE(2023, 1, 1), DATE(2026, 12, 31) )
```

**Ventajas:**
- Rango controlado: sabes exactamente qué fechas contiene el calendario.
- Permite extender el calendario hacia el futuro para análisis de presupuesto o previsión.
- Más predecible cuando el modelo crece y se añaden nuevas tablas.

**Inconvenientes:**
- Hay que actualizar el rango manualmente cuando los datos superen los límites definidos.

### La versión dinámica: CALENDAR con TODAY()

Para modelos en producción que refrescan datos periódicamente, el rango puede definirse de forma semi-dinámica:

```dax
Calendario =
CALENDAR(
    DATE( 2023, 1, 1 ),
    EOMONTH( TODAY(), 12 )     -- 12 meses desde hoy hacia el futuro
)
```

`EOMONTH(TODAY(), 12)` devuelve el último día del mes que está 12 meses por delante. El calendario siempre cubre hasta un año en el futuro sin intervención manual.

> **Para HotelesMediterraneum:** usaremos `CALENDAR(DATE(2023,1,1), EOMONTH(TODAY(),12))` para que el modelo pueda usarse en análisis de presupuesto y previsión de temporada, no solo para datos históricos.

## 2. Crear el calendario en Power Query (M)

La tabla `Calendario` se puede crear igualmente en **Power Query** usando el lenguaje M. Esta opción tiene una ventaja importante: el calendario se genera antes de cargar el modelo, lo que facilita añadir datos de festivos desde fuentes externas (Excel, SharePoint, web) sin mezclar DAX con fuentes de datos.

### 2.1 Crear la consulta en blanco

En Power BI Desktop: pestaña **Home → Transform data** para abrir Power Query.

En Power Query: **Home → New source → Blank query**. Se abre el editor de fórmulas con `= null`.

Renombra la consulta en el panel de propiedades (derecha) como `Calendario_PQ` (trabajaremos en paralelo para comparar; al final mantendremos solo una).

### 2.2 Generar la lista de fechas

En la barra de fórmulas, escribe la siguiente expresión M completa:

```
let
    FechaInicio  = #date(2023, 1, 1),
    FechaFin     = Date.EndOfMonth(Date.AddMonths(DateTime.Date(DateTime.LocalNow()), 12)),
    TotalDias    = Duration.Days(FechaFin - FechaInicio) + 1,
    ListaFechas  = List.Dates(FechaInicio, TotalDias, #duration(1, 0, 0, 0)),
    TablaFechas  = Table.FromList(ListaFechas, Splitter.SplitByNothing(), {"Date"}),
    TipoFecha    = Table.TransformColumnTypes(TablaFechas, {{"Date", type date}})
in
    TipoFecha
```

**Cómo funciona paso a paso:**

| Paso | Variable | Qué hace |
|---|---|---|
| 1 | `FechaInicio` | Define el 1 de enero de 2023 como punto de partida |
| 2 | `FechaFin` | Calcula el último día del mes 12 meses desde hoy |
| 3 | `TotalDias` | Calcula cuántos días hay entre las dos fechas |
| 4 | `ListaFechas` | Genera la lista de fechas, una por día |
| 5 | `TablaFechas` | Convierte la lista en tabla con columna `Date` |
| 6 | `TipoFecha` | Asegura que `Date` es tipo `date` (no texto) |

### 2.3 Añadir columnas en Power Query

Con la tabla `Calendario_PQ` activa, añade columnas desde **Add column**:

**Año:** `Add column → Date → Year → Year` → renombrar a `Año`.

**Mes (número):** `Add column → Date → Month → Month` → renombrar a `Mes`.

**Nombre del mes:** `Add column → Date → Month → Name of Month` → renombrar a `NombreMes`.

**Trimestre:** `Add column → Date → Quarter → Quarter` → renombrar a `NumTrimestre`. Luego añade una columna personalizada:
`Add column → Custom column`:
```
"T" & Text.From([NumTrimestre])
```
Renombra a `Trimestre`. Elimina la columna auxiliar `NumTrimestre`.

**Semana ISO (número):** `Add column → Custom column`:
```
Date.WeekOfYear([Date], Day.Monday)
```
Renombra a `Semana`.

**Día de la semana (número):** `Add column → Custom column`:
```
Date.DayOfWeek([Date], Day.Monday) + 1
```
Renombra a `DiaSemana`. (Power Query devuelve 0–6; el +1 lo convierte en 1–7 igual que DAX.)

**Nombre del día:** `Add column → Date → Day → Name of Day` → renombrar a `NombreDia`.

**Fin de semana:** `Add column → Custom column`:
```
if [DiaSemana] >= 6 then "Fin de semana" else "Entre semana"
```
Renombra a `EsFinDeSemana`.

**AñoMes (texto para etiquetas):** `Add column → Custom column`:
```
Text.PadStart(Text.From([Año]), 4, "0") & "-" &
Text.PadStart(Text.From([Mes]), 2, "0")
```
Renombra a `AñoMes`.

> [CAPTURA 2.1 — Panel de Power Query con la consulta Calendario_PQ activa. Las columnas visibles son: Date, Año, Mes, NombreMes, NumTrimestre, Trimestre, Semana, DiaSemana, NombreDia, EsFinDeSemana, AñoMes. El panel de Applied Steps a la derecha muestra los pasos encadenados.]

### 2.4 DAX vs Power Query para el calendario: ¿cuál elegir?

| Criterio | DAX (CALENDARAUTO / CALENDAR) | Power Query (M) |
|---|---|---|
| Velocidad de creación | Más rápido para tablas simples | Más verboso inicialmente |
| Añadir datos externos (festivos, temporadas desde Excel) | Requiere combinar con una segunda tabla | Merge nativo en Power Query |
| Legibilidad para equipos mixtos | Solo accesible desde Power BI | Editable por analistas de Excel |
| Actualización automática del rango | Igual en ambos con `TODAY()` | Igual con `DateTime.LocalNow()` |

> **Recomendación para HotelesMediterraneum:** mantén el calendario en DAX con `CALENDAR()`. Es más simple para un modelo que no tiene fuentes externas de festivos. Si en el futuro la empresa importa un calendario de festivos desde un sistema central, migra a Power Query.

Para esta sesión seguiremos trabajando con el calendario en DAX. Cierra Power Query sin aplicar (`Close → Discard changes`) o elimina la consulta `Calendario_PQ` antes de cerrar.

## 3. Columnas de negocio hotelero en el calendario

El calendario básico tiene columnas temporales genéricas. Un calendario profesional para hotelería añade columnas que el negocio usa para segmentar el análisis. Las añadimos en la vista **Data** de `Calendario` con **New column**.

### 3.1 Temporada hotelera

La temporada divide el año en periodos con distinta demanda. Para el grupo Mediterráneo (hoteles en costa sur, costa levantina, Barcelona y Bilbao):

```dax
Temporada =
SWITCH(
    TRUE(),
    MONTH(Calendario[Date]) IN {7, 8},                           "Alta",
    MONTH(Calendario[Date]) IN {6, 9},                           "Media-Alta",
    MONTH(Calendario[Date]) IN {3, 4, 5, 10},                    "Media",
    MONTH(Calendario[Date]) IN {11, 12, 1, 2},                   "Baja"
)
```

Esta columna permite crear visualizaciones de revenue por temporada sin escribir `CALCULATE` con rangos de fechas explícitos. Los usuarios de negocio pueden filtrar por "Alta", "Media" o "Baja" desde un slicer.

### 3.2 Festivos nacionales de España

Los festivos son días donde la demanda hotelera se comporta de forma diferente al resto. Los añadimos como una columna calculada con las fechas fijas:

```dax
EsFestivo =
VAR _dia  = DAY(Calendario[Date])
VAR _mes  = MONTH(Calendario[Date])
RETURN
IF(
    (_dia = 1  && _mes = 1)  ||   -- Año Nuevo
    (_dia = 6  && _mes = 1)  ||   -- Reyes
    (_dia = 1  && _mes = 5)  ||   -- Día del Trabajo
    (_dia = 15 && _mes = 8)  ||   -- Asunción
    (_dia = 12 && _mes = 10) ||   -- Fiesta Nacional
    (_dia = 1  && _mes = 11) ||   -- Todos los Santos
    (_dia = 6  && _mes = 12) ||   -- Constitución
    (_dia = 8  && _mes = 12) ||   -- Inmaculada
    (_dia = 25 && _mes = 12),     -- Navidad
    "Festivo",
    "Laborable"
)
```

> Los festivos variables (Semana Santa, Corpus) cambian de fecha cada año. Para incluirlos, lo correcto es importar un Excel con las fechas exactas año a año y hacer un merge en Power Query. Como simplificación para esta sesión, usamos solo los festivos de fecha fija.

### 3.3 Tipo de semana (puentes y festivos largos)

Para el análisis de operaciones hoteleras es útil identificar los puentes:

```dax
TipoSemana =
SWITCH(
    TRUE(),
    Calendario[EsFestivo] = "Festivo",                     "Festivo",
    Calendario[EsFinDeSemana] = "Fin de semana",            "Fin de semana",
    Calendario[EsFinDeSemana] = "Entre semana",             "Entre semana"
)
```

### 3.4 Número de semana ISO

El estándar ISO 8601 define la semana 1 como la que contiene el primer jueves de enero. Es diferente de la semana del año simple. Para informes que se envían a partners europeos, la semana ISO es el estándar:

```dax
SemanaISO =
VAR _isoYear = YEAR( Calendario[Date] - WEEKDAY(Calendario[Date], 2) + 4 )
VAR _isoWeek = INT( ( Calendario[Date] - DATE(_isoYear, 1, 4) +
               WEEKDAY( DATE(_isoYear, 1, 4), 2) ) / 7 ) + 1
RETURN
    _isoWeek
```

> Esta fórmula implementa el algoritmo ISO 8601 completo en DAX. Es más compleja que `WEEKNUM(date, 2)` pero produce resultados correctos en las semanas 1 y 52/53 de diciembre/enero, donde `WEEKNUM` puede divergir del estándar.

### 3.5 Resumen de columnas del calendario profesional

| Columna | Tipo | Descripción |
|---|---|---|
| `Date` | Date | Clave primaria del calendario |
| `Año` | Whole number | Año de la fecha |
| `Mes` | Whole number | Número de mes (1–12), oculta |
| `NombreMes` | Text | Nombre del mes, ordenado por `Mes` |
| `Trimestre` | Text | "T1", "T2", "T3", "T4" |
| `Semana` | Whole number | Semana del año (ISO), oculta |
| `SemanaISO` | Whole number | Semana ISO 8601 |
| `DiaSemana` | Whole number | Número de día (1=lunes, 7=domingo), oculta |
| `NombreDia` | Text | Nombre del día, ordenado por `DiaSemana` |
| `EsFinDeSemana` | Text | "Fin de semana" / "Entre semana" |
| `Temporada` | Text | "Alta" / "Media-Alta" / "Media" / "Baja" |
| `EsFestivo` | Text | "Festivo" / "Laborable" |
| `TipoSemana` | Text | "Festivo" / "Fin de semana" / "Entre semana" |
| `AñoMes` | Text | "2024-03" para etiquetas de eje |

## 4. Múltiples columnas de fecha y relaciones inactivas

### 4.1 El problema: tres columnas de fecha en fact_reservas

La tabla `fact_reservas` tiene tres columnas de fecha:

| Columna | Significado |
|---|---|
| `checkin_date` | Fecha de llegada del cliente al hotel |
| `checkout_date` | Fecha de salida del cliente del hotel |
| `booking_date` | Fecha en que se realizó la reserva |

El modelo solo puede tener **una relación activa** entre `fact_reservas` y `Calendario`. La relación activa es la que se usa por defecto en todos los visuales y medidas. Las demás relaciones existen en el modelo como **inactivas** y solo se activan cuando una medida DAX las invoca explícitamente con `USERELATIONSHIP`.

### 4.2 Crear las relaciones inactivas

En la vista **Model**, arrastra:

- `fact_reservas[checkout_date]` sobre `Calendario[Date]` → Power BI creará la relación pero la marcará automáticamente como inactiva (línea discontinua) porque ya existe una relación activa con la misma tabla `Calendario`.
- `fact_reservas[booking_date]` sobre `Calendario[Date]` → igualmente inactiva.

> [CAPTURA 4.1 — Vista Model con tres líneas de relación entre fact_reservas y Calendario. La línea de checkin_date es sólida (relación activa). Las líneas de checkout_date y booking_date son discontinuas (relaciones inactivas). Las tres tienen la misma cardinalidad Many to one (*:1).]

Al hacer doble clic en una relación inactiva, verás el toggle **Make this relationship active** desmarcado. Power BI lo desactiva automáticamente para evitar ambigüedad de filtro cuando varias relaciones apuntan a la misma tabla.

### 4.3 USERELATIONSHIP: activar una relación inactiva desde DAX

`USERELATIONSHIP` es una función de modificación de contexto que se usa dentro de `CALCULATE`. Activa temporalmente una relación inactiva para el cálculo de esa medida específica.

**Sintaxis:**

```dax
CALCULATE(
    <expresión>,
    USERELATIONSHIP( <columna_tabla_hechos>, <columna_tabla_dimensión> )
)
```

### 4.4 Medidas con USERELATIONSHIP para HotelesMediterraneum

**Revenue por fecha de reserva (booking_date):**

```dax
[Revenue por Fecha Reserva] =
CALCULATE(
    [Revenue Total],
    USERELATIONSHIP( fact_reservas[booking_date], Calendario[Date] )
)
```

Esta medida calcula el revenue sumando las reservas según cuándo se confirmaron, no según cuándo llega el cliente. Es clave para analizar la curva de demanda: ¿con cuánta antelación se reserva la temporada alta?

**Reservas por fecha de salida (checkout_date):**

```dax
[Reservas por Fecha Salida] =
CALCULATE(
    [Reservas Totales],
    USERELATIONSHIP( fact_reservas[checkout_date], Calendario[Date] )
)
```

Útil para calcular la ocupación real de cada noche: en un gráfico por `Calendario[Date]`, esta medida cuenta cuántas reservas tenían checkout esa fecha, lo que equivale a cuántos clientes se fueron ese día.

**Noches vendidas por periodo de estancia:**

Para calcular cuántas habitaciones estaban ocupadas cada noche del año, la métrica correcta no es contar por `checkin_date` ni por `checkout_date`, sino contar las noches dentro del rango `[checkin_date, checkout_date)`. Esto requiere una técnica más avanzada (table expansion o un snapshot diario) que está fuera del alcance de esta sesión. La mencionamos para que quede claro que `USERELATIONSHIP` resuelve la selección de fecha de referencia, pero no el problema de la estancia multi-noche.

### 4.5 Ejemplo práctico: curva de antelación de reservas

Uno de los KPIs más relevantes en revenue management es la **curva de pick-up**: cuántas reservas se van acumulando para una fecha de llegada determinada, día a día desde meses antes.

Creamos dos medidas que coexisten en el mismo visual:

```dax
[Revenue por Checkin] =
[Revenue Total]
-- Usa la relación activa (checkin_date → Calendario[Date])

[Revenue por Booking] =
CALCULATE(
    [Revenue Total],
    USERELATIONSHIP( fact_reservas[booking_date], Calendario[Date] )
)
```

En un gráfico de líneas con `Calendario[AñoMes]` en el eje X, las dos medidas muestran curvas distintas:
- `[Revenue por Checkin]`: cuándo se produce la estancia (revenue devengado).
- `[Revenue por Booking]`: cuándo se confirmó la reserva (revenue comprometido).

La diferencia entre ambas curvas revela el comportamiento de antelación de los clientes. Para hoteles de negocio (Bilbao) la diferencia es pequeña (reservas de última hora). Para hoteles vacacionales (Málaga, Alicante) la diferencia es grande: las reservas de verano se confirman en enero.

> [CAPTURA 4.2 — Gráfico de líneas con dos series: "[Revenue por Checkin]" y "[Revenue por Booking]", ambas por mes. La serie de booking muestra un pico en enero-febrero mientras que la de checkin muestra el pico en julio-agosto, reflejando la antelación de las reservas de temporada alta.]

## 5. Año fiscal personalizado

### 5.1 Cuándo el año natural no es suficiente

Algunas empresas hoteleras no cierran su ejercicio el 31 de diciembre. Un grupo con mayoría de turismo de sol y playa puede usar un **año fiscal** que va del 1 de noviembre al 31 de octubre, agrupando los meses de mayor actividad (verano) en el centro del ejercicio.

### 5.2 Columna de año fiscal en el calendario

```dax
AñoFiscal =
IF(
    MONTH(Calendario[Date]) >= 11,
    "AF" & YEAR(Calendario[Date]) & "/" & (YEAR(Calendario[Date]) + 1),
    "AF" & (YEAR(Calendario[Date]) - 1) & "/" & YEAR(Calendario[Date])
)
```

Esta expresión asigna noviembre y diciembre de 2024 al ejercicio "AF2024/2025", y los meses enero–octubre de 2025 también al mismo ejercicio. La etiqueta "AF2024/2025" identifica unívocamente el año fiscal.

### 5.3 Mes fiscal (para ordenar correctamente)

Para que el año fiscal se muestre con los meses en orden correcto (noviembre = 1, diciembre = 2, enero = 3, ..., octubre = 12):

```dax
MesFiscal =
MOD( MONTH(Calendario[Date]) - 11 + 12, 12 ) + 1
```

Usa `MesFiscal` como columna de ordenación para `NombreMes` en visuales donde el eje sea el año fiscal.

### 5.4 TOTALYTD con año fiscal

La función `TOTALYTD` admite un cuarto parámetro que define cuándo termina el año. Para el año fiscal noviembre–octubre, el año termina el 31 de octubre:

```dax
[Revenue YTD Fiscal] =
TOTALYTD( [Revenue Neto], Calendario[Date], "31/10" )
```

El acumulado resetea el 1 de noviembre en lugar del 1 de enero.

> Para HotelesMediterraneum usamos año natural (enero–diciembre), así que estas columnas son opcionales. Las incluimos para que el modelo esté preparado si el cliente cambia su política de reporting.

## 7. Nuevos análisis habilitados por el calendario mejorado

### 7.1 Revenue por temporada

Con la columna `Temporada`, el análisis de estacionalidad no requiere filtros de fecha manuales:

- Slicer de `Calendario[Temporada]` → filtra todos los visuales a la temporada seleccionada.
- Gráfico de barras: `Calendario[Temporada]` en eje Y, `[Revenue Total]` en eje X → muestra de un vistazo cuánto pesa cada temporada.

### 7.2 Comparativa festivos vs. laborables

```dax
[Revenue Festivos] =
CALCULATE( [Revenue Total], Calendario[EsFestivo] = "Festivo" )

[Revenue Laborables] =
CALCULATE( [Revenue Total], Calendario[EsFestivo] = "Laborable" )

[Premium Festivo %] =
DIVIDE(
    CALCULATE( [ADR por Reserva], Calendario[EsFestivo] = "Festivo" ),
    CALCULATE( [ADR por Reserva], Calendario[EsFestivo] = "Laborable" )
) - 1
```

`[Premium Festivo %]` muestra cuánto más cobran los hoteles en festivos respecto a días laborables. En hoteles vacacionales este dato justifica la política de precios de temporada.

### 7.3 Análisis de lead time con booking_date

```dax
[Lead Time Promedio] =
AVERAGEX(
    fact_reservas,
    DATEDIFF( fact_reservas[booking_date], fact_reservas[checkin_date], DAY )
)
```

Esta medida ya existía. Combinada con `[Revenue por Fecha Reserva]` en un visual con `Calendario[AñoMes]` como eje, permite ver si el lead time medio cambia a lo largo del año y si correlaciona con la temporada.

## 8. Ejercicios prácticos

### Ejercicio 1 — Básico

## 9. Errores comunes y soluciones

| Error | Causa probable | Solución |
|---|---|---|
| Al cambiar de `CALENDARAUTO()` a `CALENDAR()`, algunas columnas calculadas dan error | El nombre de la columna principal de la tabla cambió (de `Date` a otro) | `CALENDAR()` siempre genera una columna llamada `Date`; `CALENDARAUTO()` también. Si el error persiste, verificar que la expresión de la columna usa `Calendario[Date]` y no `Calendario[Fecha]` o similar |
| `USERELATIONSHIP` da el error "A circular dependency was detected" | Se está intentando activar una relación que crea un ciclo en el modelo | Verificar el diagrama de relaciones; una relación activa ya conecta las dos tablas por otra ruta |
| Las medidas con `USERELATIONSHIP` devuelven el mismo valor que sin él | La relación inactiva no existe todavía en el modelo | Crear primero la relación (inactiva) en la vista Model antes de usar `USERELATIONSHIP` |
| El gráfico de `[Revenue por Fecha Reserva]` muestra valores para fechas muy anteriores al checkin | Correcto: las reservas se hacen meses antes del checkin; ese es el comportamiento esperado | No es un error; explicar al usuario la diferencia semántica entre booking_date y checkin_date |
| La columna `Temporada` no aparece como opción de slicer | La columna está oculta en la vista de informe | Clic derecho sobre la columna en la vista Model → desmarcar "Hide in report view" |
| La columna `EsFestivo` clasifica como "Laborable" días que deberían ser festivos | La fórmula solo cubre festivos de fecha fija; Semana Santa y festivos variables no están | Importar un CSV con las fechas exactas de todos los festivos y hacer un `LOOKUPVALUE` contra esa tabla |
| `TOTALYTD` con el parámetro de año fiscal no resetea en la fecha correcta | El parámetro debe ser el último día del año fiscal en formato `"DD/MM"` | Verificar el formato: para año fiscal que termina el 31 de octubre, usar `"31/10"`, no `"10/31"` ni `"31-10"` |
| Dos relaciones entre las mismas tablas y Power BI activa la incorrecta | Power BI activa la primera relación que detecta al importar | En la vista Model, clic en la relación correcta → doble clic → marcar "Make this relationship active" |

## 10. Lo que DAX ha hecho por debajo

**CALENDAR genera una tabla virtual que DAX almacena en memoria**

```dax
Calendario = CALENDAR(DATE(2023, 1, 1), EOMONTH(TODAY(), 12))
```

`CALENDAR` genera una tabla con una columna llamada `Date` y una fila por día. El motor la evalúa una sola vez en el momento de cargar el modelo (o al refrescarlo) y la almacena en VertiPaq como cualquier otra tabla. Las columnas calculadas que añadimos después se evalúan fila a fila en ese momento de carga: `YEAR(Calendario[Date])` se ejecuta 1.400 veces (una por día del rango) y el resultado se almacena como columna comprimida. En tiempo de consulta, los valores ya están calculados.

**"Mark as Date Table" cambia el comportamiento del motor para esa tabla**

Cuando marcas `Calendario` como Date Table, Power BI registra internamente que `Calendario[Date]` es la columna de clave de fecha del modelo. A partir de ese momento:

1. El motor valida que `Calendario[Date]` no tiene nulos, no tiene duplicados y es contigua (sin huecos de días). Si falla la validación, el marcado no se completa.
2. Las funciones de Time Intelligence (`TOTALYTD`, `DATEADD`, `SAMEPERIODLASTYEAR`) pueden usar `Calendario[Date]` como argumento. Sin el marcado, el motor no puede garantizar que la tabla sea apta para esas funciones.
3. Power BI desactiva las jerarquías de fecha automáticas que generaría por defecto sobre columnas de tipo `date` en otras tablas, usando en su lugar la tabla marcada.

El equivalente conceptual en SQL sería configurar un índice de tipo calendar en el servidor y marcar una tabla como la fuente oficial de fechas para el esquema.

**USERELATIONSHIP activa una relación inactiva solo durante esa evaluación de CALCULATE**

```dax
[Revenue por Fecha Reserva] =
CALCULATE(
    [Revenue Total],
    USERELATIONSHIP(fact_reservas[booking_date], Calendario[Date])
)
```

Cuando el motor evalúa esta medida, desactiva temporalmente la relación activa `fact_reservas[checkin_date] → Calendario[Date]` y activa la relación `fact_reservas[booking_date] → Calendario[Date]`. El filtro de `Calendario[Date]` que venga del visual (por ejemplo, "mes = junio 2024") ahora se propaga a través de `booking_date` en lugar de `checkin_date`. Al terminar la evaluación, la relación activa vuelve a ser la original.

Esto significa que en un gráfico con `Calendario[NombreMes]` en el eje y ambas medidas `[Revenue Total]` y `[Revenue por Fecha Reserva]`, la primera agrupa las reservas por mes de llegada del cliente y la segunda por mes en que se hizo la reserva. Las dos curvas pueden divergir significativamente en hoteles con alta antelación.

**Las relaciones inactivas existen en el modelo pero no propagan filtros por defecto**

Power BI puede almacenar múltiples relaciones entre las mismas dos tablas, pero solo una puede estar activa. Las inactivas aparecen en la vista Model como líneas discontinuas. No propagan ningún filtro de forma automática: ningún slicer, ningún visual y ninguna medida las usa a menos que `USERELATIONSHIP` las active explícitamente en esa evaluación concreta.
