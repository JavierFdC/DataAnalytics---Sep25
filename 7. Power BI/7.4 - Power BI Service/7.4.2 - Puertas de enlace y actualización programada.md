# Power BI: Puertas de enlace y actualización programada

**Bloque 7 -- Power BI | Sesión 14 de 21**

---

## Introducción

En la sesión 7.4.1 publicamos el informe de HotelesMediterraneum en el servicio y lo compartimos con los directores de hotel a través de la App. Al cerrar esa sesión, el modelo semántico en la nube contiene los datos del momento de la publicación. Cuando el analista abre el informe mañana, los datos siguen siendo los de ayer. Cuando lo abra el director general la semana que viene, los datos pueden tener una semana de antigüedad.

Power BI Service no puede leer directamente `\\servidor\datos\reservas.csv` porque ese archivo vive en la red privada de HotelesMediterraneum, detrás de un firewall, en un servidor que no está expuesto a Internet. La nube de Microsoft no puede entrar en esa red. El **On-Premises Data Gateway** invierte la relación: en lugar de que el servicio entre a la red, es la red la que llama al servicio. El gateway es un proceso de Windows instalado en un servidor de la red interna que mantiene una conexión saliente persistente con el servicio de Power BI y actúa de intermediario: recibe las peticiones de refresco, accede al origen local, y devuelve los datos al servicio en la nube.

El objetivo de esta sesión es completar el paso 5 del pipeline de publicación que dejamos pendiente en 7.4.1:

```
5. OPERACIÓN (→ sesión 7.4.2)
   └── Gateway ejecuta Scheduled Refresh a las 06:00 diariamente
```

Cuando terminemos, el informe del CRO mostrará cada mañana los datos del día anterior sin que nadie tenga que publicar manualmente desde Desktop.

### Objetivos de la sesión

- Entender qué es el On-Premises Data Gateway y en qué se diferencia del Personal Gateway.
- Instalar y registrar el gateway en un servidor de la red de HotelesMediterraneum.
- Configurar las credenciales de origen de datos en el servicio.
- Programar la actualización automática del modelo semántico.
- Monitorizar el historial de actualizaciones y configurar notificaciones de fallo.
- Diagnosticar y resolver los errores más frecuentes de gateway y refresco.

### Prerequisitos

- `HotelesMediterraneum_7.4.1_resuelto.pbix` publicado en el workspace **HotelesMediterraneum - Producción**.
- Acceso de administrador a un servidor Windows de la red interna donde está `\\servidor\datos\reservas.csv`.
- Cuenta de Power BI con licencia **Pro** o **Premium Per User** y permisos de Admin en el workspace.
- El servidor candidato para el gateway tiene acceso a Internet (saliente, puerto 443) y acceso a la carpeta de red donde vive el CSV.

## 1. Conceptos previos: por qué el gateway existe

### 1.1 El problema de accesibilidad

Cuando Power BI Service ejecuta una actualización programada, necesita conectarse al origen de datos para leer los nuevos datos. Si el origen está en la nube —Azure Blob, SharePoint Online, una API pública— el servicio puede conectarse directamente. Si el origen está en la red interna —un SQL Server local, una carpeta de red, un Oracle en el centro de datos— el servicio no tiene ruta de acceso.

```
┌─────────────────────────────┐          ┌─────────────────────────────┐
│      Red interna            │          │  Power BI Service (nube)    │
│                             │          │                             │
│  \\servidor\datos\          │    ✗     │  Scheduled Refresh          │
│  reservas.csv               │◄─────────│  (no puede entrar)          │
│                             │          │                             │
│  SQL Server 192.168.1.10    │          │                             │
└─────────────────────────────┘          └─────────────────────────────┘
```

### 1.2 La solución: conexión saliente invertida

El gateway invierte la dirección. En lugar de que el servicio intente entrar, es el gateway el que abre una conexión saliente persistente hacia los servidores de Microsoft (por HTTPS, puerto 443). Esa conexión siempre está activa mientras el gateway esté funcionando. Cuando el servicio necesita datos, envía la solicitud por esa conexión ya abierta; el gateway la recibe, va a buscar los datos localmente, y los devuelve.

```
┌─────────────────────────────┐          ┌─────────────────────────────┐
│      Red interna            │          │  Power BI Service (nube)    │
│                             │  HTTPS   │                             │
│  ┌──────────────────┐       │◄─────────►  Scheduled Refresh          │
│  │ On-Premises      │ ◄────►│          │  (solicitud → respuesta)    │
│  │ Data Gateway     │       │          │                             │
│  └──────────────────┘       │          └─────────────────────────────┘
│        │                    │
│        ▼                    │
│  \\servidor\datos\          │
│  reservas.csv               │
└─────────────────────────────┘
```

Ventajas de este diseño: no hay que abrir puertos de entrada en el firewall, no hay que exponer servidores internos a Internet, y el tráfico de datos va cifrado.

### 1.3 Gateway estándar vs. Personal Gateway

Microsoft ofrece dos tipos de gateway. La diferencia no es menor:

| | Gateway estándar (On-Premises Data Gateway) | Personal Gateway |
|---|---|---|
| **Instalación** | En un servidor compartido de la organización | En el PC personal del analista |
| **Usuarios** | Múltiples usuarios y múltiples modelos semánticos | Solo el usuario que lo instala |
| **Alta disponibilidad** | Sí (clúster de gateways) | No |
| **Dataflows de Power BI** | Sí | No |
| **Caso de uso** | Producción organizacional | Pruebas personales, uso individual |
| **Recomendado para HotelesMediterraneum** | **Sí** | No (no escala, no resiste caídas) |

En esta sesión instalamos el **gateway estándar**. El Personal Gateway existe y funciona para pruebas individuales, pero nunca debe usarse en producción: si el PC del analista se apaga o se va de vacaciones, el refresco falla.

## 2. Preparar el servidor para el gateway

### 2.1 Requisitos del servidor

El gateway necesita un servidor que cumpla estos requisitos mínimos:

| Requisito | Mínimo | Recomendado para HotelesMediterraneum |
|---|---|---|
| **Sistema operativo** | Windows 8.1 / Windows Server 2012 R2 | Windows Server 2019 o 2022 |
| **CPU** | 4 núcleos | 8 núcleos |
| **RAM** | 8 GB | 16 GB |
| **Disco** | 10 GB libres | 40 GB SSD (para caché de consultas) |
| **Red** | Acceso a Internet (saliente 443) | 100 Mbps o superior |
| **Frameworks** | .NET Framework 4.7.2+ | .NET Framework 4.8 |

El servidor no tiene que ser un equipo dedicado exclusivamente al gateway. En HotelesMediterraneum, el servidor BI existente (`SERVIDOR-BI-01`, Windows Server 2022 con 16 GB RAM) es el candidato natural porque ya tiene acceso a la carpeta de red `\\servidor\datos\`.

### 2.2 Verificar acceso al origen de datos desde el servidor

Antes de instalar el gateway, hay que confirmar que el servidor puede leer el origen de datos. Desde `SERVIDOR-BI-01`, abrimos el Explorador de Windows y navegamos a `\\servidor\datos\`. Si podemos abrir `reservas.csv`, el acceso está garantizado. Si no podemos, hay que resolver los permisos de red **antes** de instalar el gateway: el gateway no puede acceder a lo que el servidor no puede acceder.

```powershell
# Verificación rápida desde PowerShell en SERVIDOR-BI-01
Test-Path "\\servidor\datos\reservas.csv"
# Debe devolver: True
```

### 2.3 Cuenta de servicio para el gateway

El gateway se ejecuta como un servicio de Windows. Puede ejecutarse con la cuenta del sistema (`NT SERVICE\PBIEgwService`) o con una cuenta de dominio específica. Para HotelesMediterraneum usamos una cuenta de servicio dedicada:

- **Cuenta:** `DOMINIO\svc-powerbi`
- **Contraseña:** gestionada por el equipo de IT
- **Permisos necesarios:** lectura sobre `\\servidor\datos\` y permiso "Iniciar sesión como servicio" en el servidor

Usar una cuenta de servicio dedicada (en lugar de la cuenta personal del analista) tiene dos ventajas críticas: los permisos no dependen de que nadie cambie su contraseña personal, y se puede revocar la cuenta de servicio si hay un incidente de seguridad sin afectar a nadie más.

## 3. Instalar el On-Premises Data Gateway

### 3.1 Descargar el instalador

En el servidor `SERVIDOR-BI-01`, abrimos un navegador y vamos a **Power BI Service > Settings (engranaje) > Manage gateways > + Add data gateway**.

El servicio detecta automáticamente que no tenemos ningún gateway instalado y ofrece el enlace de descarga del instalador. También podemos descargarlo desde la página de documentación de Microsoft.

> [CAPTURA 3.1 — Pantalla de "Manage gateways" en Power BI Service mostrando la vista vacía con el mensaje "No gateways found" y el botón "+ Add data gateway" resaltado en la parte superior derecha. Un enlace "Download" visible para descargar el instalador.]

El instalador se llama `GatewayInstall.exe` y pesa aproximadamente 150 MB.

### 3.2 Ejecutar el instalador

Ejecutamos `GatewayInstall.exe` con privilegios de administrador. El asistente de instalación tiene cuatro pasos:

**Paso 1: Tipo de gateway.** Seleccionamos **On-premises data gateway (recommended)**, no el Personal Gateway.

> [CAPTURA 3.2 — Primera pantalla del asistente de instalación del gateway con las dos opciones: "On-premises data gateway (recommended)" seleccionada con un radio button azul, y "On-premises data gateway (personal mode)" sin seleccionar. Breve descripción de cada opción debajo.]

**Paso 2: Ruta de instalación.** Aceptamos la ruta por defecto (`C:\Program Files\On-premises data gateway`) o la cambiamos si la política de IT lo requiere.

**Paso 3: Cuenta de servicio.** El instalador pregunta con qué cuenta ejecutar el servicio de Windows. Introducimos `DOMINIO\svc-powerbi` y su contraseña. El instalador verificará que la cuenta tiene permisos de inicio de sesión como servicio y los añadirá si es necesario.

**Paso 4: Confirmación.** El instalador muestra el resumen de la configuración. Pulsamos **Install**. El proceso tarda entre 2 y 5 minutos.

Al terminar, el instalador lanza automáticamente la pantalla de configuración del gateway.

### 3.3 Iniciar sesión y registrar el gateway

La pantalla de configuración del gateway pide iniciar sesión con la **cuenta de Power BI** del administrador (no con la cuenta de servicio). Iniciamos sesión con la misma cuenta que tiene acceso al workspace de HotelesMediterraneum.

Una vez autenticados, el asistente pide registrar el gateway:

| Campo | Valor |
|---|---|
| **Name** | `GW-HotelesMediterraneum-01` |
| **Recovery key** | Una clave de 8+ caracteres que debemos guardar en un lugar seguro |
| **Recovery key confirmation** | Repetir la clave |
| **Region** | West Europe (la misma región donde está nuestro tenant de Power BI) |

> [CAPTURA 3.3 — Pantalla de registro del gateway con los campos Name, Recovery key y Confirm recovery key rellenos. Un aviso visible debajo de "Recovery key" que dice "Store this key in a safe place. You'll need it to recover or move this gateway." La región seleccionada en el desplegable Region.]

La **recovery key** es crítica: si el servidor falla y hay que migrar el gateway a otro servidor, esta clave permite restaurar todas las configuraciones de conexión y credenciales. Sin ella, hay que reconfigurar todo desde cero. La guardamos en la bóveda de contraseñas del equipo de IT.

Pulsamos **Configure**. El gateway se registra en el servicio de Power BI y aparece en la lista de gateways disponibles.

> [CAPTURA 3.4 — Pantalla final de configuración del gateway mostrando el mensaje "The gateway GW-HotelesMediterraneum-01 is online and ready to be used." con un icono verde de check. El estado del servicio de Windows visible en la parte inferior como "Running".]

Desde los tres puntos junto al gateway > **Settings**:

- **Allow user's cloud data sources to refresh through this gateway cluster:** activar si queremos que el gateway también gestione fuentes en la nube para el mismo modelo semántico (útil si en el futuro añadimos un origen en Azure junto al CSV local).

| Rol | Puede hacer |

| **Usuario** | Usar el gateway para conectar sus propios modelos semánticos a fuentes existentes |

## 5. Configurar el origen de datos en el gateway

El gateway ya está registrado, pero aún no sabe de qué orígenes de datos es responsable. Hay que darlos de alta explícitamente.

### 5.1 Añadir la fuente de datos del CSV

En **Manage gateways > GW-HotelesMediterraneum-01 > + Add data source**:

| Campo | Valor |
|---|---|
| **Data source name** | `reservas-csv-red` |
| **Data source type** | `File` |
| **File path** | `\\servidor\datos\reservas.csv` |
| **Authentication method** | `Windows` |
| **Username** | `DOMINIO\svc-powerbi` |
| **Password** | Contraseña de la cuenta de servicio |

> [CAPTURA 5.1 — Formulario "New data source" con los campos rellenados: el tipo "File" seleccionado en el desplegable, la ruta UNC en el campo "File path", el método "Windows" en Authentication y los campos de usuario y contraseña. El botón "Add" visible en la parte inferior.]

Pulsamos **Add**. El gateway inmediatamente intenta conectar con la ruta para validar las credenciales. Si la conexión es exitosa, aparece el mensaje "Connection successful" en verde.

Si aparece "Connection failed", las causas más habituales son:
- La ruta UNC no existe o el servidor la ha movido.
- La cuenta `svc-powerbi` no tiene permisos de lectura en esa carpeta.
- El servidor donde está el gateway no puede resolver el nombre `\\servidor\` por DNS.

### 5.2 Gestionar usuarios de la fuente de datos

Dentro de la fuente de datos recién creada, en la pestaña **Users**, añadimos qué usuarios de Power BI pueden usar esta fuente para sus modelos semánticos. Añadimos el email de todos los analistas del equipo de Revenue que puedan necesitar publicar modelos semánticos que consuman este CSV.

Si no se añade un usuario aquí, cuando intente configurar el refresco de su modelo semántico no verá esta fuente de datos disponible en la lista de gateways.

## 7. Configurar la actualización programada

Con el gateway vinculado al modelo, ya podemos configurar la actualización automática. Seguimos en la página de **Settings** del modelo semántico.

### 7.1 La sección Refresh

Bajamos a la sección **Refresh** en el panel de Settings.

Aquí encontramos dos opciones principales:

| Opción | Descripción |
|---|---|
| **Keep your data up to date** | Toggle para activar o desactivar la actualización programada |
| **Refresh frequency** | Con qué periodicidad se refresca (Daily, Weekly, o por intervalos si es Premium) |

Activamos el toggle **Keep your data up to date**.

### 7.2 Configurar la frecuencia y los horarios

Con la frecuencia **Daily** seleccionada:

| Campo | Valor para HotelesMediterraneum |
|---|---|
| **Time zone** | (UTC+01:00) Madrid |
| **Refresh times** | 06:00 |

Añadimos la hora haciendo clic en **Add another time** y escribiendo `06:00`. Para HotelesMediterraneum es suficiente una actualización diaria: los datos de reservas de la noche anterior llegan al servidor en un proceso batch que termina a las 05:30. El refresco a las 06:00 garantiza que cuando los directores lleguen a las 08:00, el informe ya muestra los datos del día.

> [CAPTURA 7.1 — Sección "Refresh" en el panel Settings del modelo semántico. El toggle "Keep your data up to date" activado en azul. La frecuencia "Daily" seleccionada, la zona horaria "(UTC+01:00) Madrid" en el desplegable y la hora "06:00" en la lista de "Refresh times". El botón "Add another time" visible debajo por si se necesitan más franjas horarias.]

**¿Cuántos refrescos puedo programar?** Con licencia **Pro**, el límite es 8 refrescos por día por modelo semántico (en intervalos de mínimo 30 minutos). Con **Premium Per User** o **Premium (capacidad)** el límite sube a 48 refrescos diarios (cada 30 minutos). Para HotelesMediterraneum, con un solo refresco diario a las 06:00, estamos muy por debajo de cualquier límite.

### 7.3 Notificaciones de fallo de actualización

Bajamos a la sección **Send refresh failure notifications to**:

- **Dataset owner:** enviará una notificación al propietario del modelo semántico cuando falle un refresco. Activamos esta opción.
- **These contacts:** podemos añadir emails adicionales. Añadimos al lead del equipo de analytics y al responsable del gateway en IT.

> [CAPTURA 7.2 — Sección "Send refresh failure notifications to" con el toggle "Dataset owner" activado y el campo "These contacts" con dos emails añadidos del equipo. Aclaración visible de que las notificaciones se envían después del primer fallo, no en cada intento.]

Pulsamos **Apply**. La actualización programada está configurada.

### 8.1 El historial de actualizaciones

En el workspace, junto al modelo semántico, hacemos clic en los tres puntos > **Refresh history** (o dentro de Settings, en la sección Refresh > **Refresh history**).

El historial muestra cada actualización ejecutada:

| Columna | Qué información da |
|---|---|
| **Start time** | Cuándo empezó la actualización |
| **End time** | Cuándo terminó |
| **Duration** | Cuánto tardó |
| **Status** | Completed / Failed / Cancelled |
| **Triggered by** | Scheduled (automático) / Manual / API |

> [CAPTURA 8.1 — Modal "Refresh history" con una lista de actualizaciones. Varias filas con estado "Completed" en verde y duración de 2-3 minutos. Una fila con estado "Failed" en rojo. Al hacer clic en la fila fallida, se expande un mensaje de error detallado.]

Al hacer clic en una actualización fallida se expande un mensaje de error detallado. Este mensaje es la primera herramienta de diagnóstico cuando algo va mal.

### 8.2 Actualización manual para verificar

Antes de esperar al refresco automático de las 06:00, verificamos que todo funciona ejecutando un refresco manual. En el workspace, junto al modelo semántico: tres puntos > **Refresh now**.

Power BI inicia el proceso de actualización. Después de 1-3 minutos (dependiendo del tamaño del CSV), el estado debe cambiar a "Completed". Comprobamos el historial para confirmarlo.

Si el refresco manual funciona, el automático funcionará también. Si el manual falla, tenemos el mensaje de error para diagnosticar antes de que llegue el lunes por la mañana.

### 8.3 Estado del modelo semántico en el workspace

En la lista del workspace, el modelo semántico muestra debajo de su nombre la fecha y hora del último refresco exitoso. Es una referencia rápida para confirmar que los datos están al día sin entrar en el historial completo.

## 9. Gateway: operación y mantenimiento

### 9.1 Actualizaciones del gateway

Microsoft publica una nueva versión del gateway cada mes, generalmente el segundo martes. El gateway avisa cuando hay una versión más nueva disponible, tanto en la aplicación de configuración del servidor como en el panel de **Manage gateways** del servicio.

Política recomendada para HotelesMediterraneum:
- Actualizar el gateway dentro de los 30 días siguientes a cada release.
- No actualizar en lunes (el refresco crítico es los lunes temprano).
- Mantener las dos últimas versiones soportadas: Microsoft da soporte a las últimas seis versiones. Quedarse muy atrás genera problemas de compatibilidad con conectores nuevos.

### 9.2 Clúster de gateways para alta disponibilidad

El gateway instalado en `SERVIDOR-BI-01` es un único punto de fallo: si el servidor tiene una caída de mantenimiento o un fallo hardware, el refresco no se ejecuta y el informe queda desactualizado.

Para evitarlo, se puede crear un **clúster de gateways**: dos o más gateways registrados bajo el mismo nombre de clúster. Si uno falla, el servicio enruta automáticamente las peticiones al otro.

Para añadir un segundo gateway al clúster:
1. Instalar el gateway en un segundo servidor (`SERVIDOR-BI-02`).
2. En la pantalla de registro, en lugar de crear un nuevo gateway, seleccionar **Add to an existing gateway cluster**.
3. Introducir el nombre del clúster (`GW-HotelesMediterraneum-01`) y la recovery key del gateway existente.

El resultado es un clúster con dos miembros. El balanceo de carga es automático y la conmutación por error es transparente para el servicio de Power BI.

> Para HotelesMediterraneum, con 40 hoteles y un único CSV de reservas, un clúster de dos nodos es suficiente y proporcional al riesgo. Organizaciones con cientos de modelos semánticos y orígenes de datos críticos suelen tener clústeres de tres o más nodos.

### 9.3 Monitorizar el estado del gateway

En **Manage gateways** del servicio se puede ver si cada miembro del clúster está online o offline. Es buena práctica incluir la revisión del estado del gateway en el checklist operativo semanal del equipo de analytics.

Adicionalmente, el gateway escribe logs locales en `C:\Windows\ServiceProfiles\PBIEgwService\AppData\Local\Microsoft\On-premises data gateway\`. Estos logs son la fuente de diagnóstico detallado cuando un error del servicio no es suficientemente descriptivo.

## 10. Orígenes de datos en la nube: cuándo no necesitas gateway

Es importante entender que el gateway es solo necesario para orígenes **locales** (on-premises). Si los datos de HotelesMediterraneum estuvieran en la nube, la configuración sería más simple.

| Origen | ¿Necesita gateway? | Cómo se configura |
|---|---|---|
| Archivo CSV en SharePoint Online | No | Credenciales de cuenta organizacional directamente en Service |
| Archivo CSV en OneDrive (cuenta Microsoft 365) | No | Autenticación OAuth desde Service |
| Azure Blob Storage | No | Clave de acceso o SAS token en Settings del modelo |
| Azure SQL Database | No | Cadena de conexión y credenciales en Settings |
| SQL Server local | Sí | Gateway + fuente de datos de tipo SQL Server |
| Carpeta de red local | Sí | Gateway + fuente de datos de tipo File (como en esta sesión) |
| Oracle local | Sí | Gateway + driver ODAC instalado en el servidor del gateway |

Para HotelesMediterraneum, si en el futuro el equipo de IT migra el CSV a SharePoint Online, el gateway dejaría de ser necesario para ese origen concreto. El gateway puede convivir con orígenes cloud y locales al mismo tiempo.

## 11. Actualización incremental (introducción)

La actualización completa que acabamos de configurar carga **todos los datos del CSV** en cada refresco. Con 20.000 reservas el proceso dura 2-3 minutos. Con 2 millones de reservas podría tardar 30 minutos o más, y estaríamos procesando registros históricos de 2018 que no han cambiado desde la sesión 7.1.

La **actualización incremental** resuelve esto: en lugar de recargar todo, solo recarga el rango de fechas reciente. Power BI Service comparte la configuración de los datos históricos y solo pide al gateway los datos nuevos o modificados.

La actualización incremental se configura en Power BI Desktop antes de publicar, usando parámetros especiales `RangeStart` y `RangeEnd`. Requiere que el origen de datos soporte el plegado de consultas (query folding), lo que los archivos CSV locales no soportan de forma nativa, pero sí lo hace SQL Server, por ejemplo.

> La configuración detallada de la actualización incremental se aborda en la **sesión 7.4.5 — Rendimiento y optimización** del bloque, cuando el modelo de HotelesMediterraneum haya crecido lo suficiente para necesitarla.

## 12. Flujo operativo completo de HotelesMediterraneum

Al terminar esta sesión, el ciclo completo de operación diaria de HotelesMediterraneum es:

```
05:00 — Proceso batch del sistema de reservas escribe los datos del día anterior
        en \\servidor\datos\reservas.csv

06:00 — Power BI Service lanza la actualización programada del modelo semántico
        │
        └── Solicita datos al gateway GW-HotelesMediterraneum-01
              │
              └── El gateway lee \\servidor\datos\reservas.csv
                    │
                    └── Devuelve los datos al modelo semántico en la nube
                          │
                          └── El motor VertiPaq comprime y almacena los nuevos datos

~06:05 — Actualización completada. Historial muestra "Completed (2m 47s)"

06:05 — Email automático de Power BI a los suscriptores del informe ejecutivo
        (configurado en 7.4.1, Extra 1)

08:00 — Los directores de hotel abren la App en el móvil o el navegador
        y ven los datos del día anterior completamente actualizados

Si la actualización falla (≥1 intento fallido):
└── Notificación automática al equipo de analytics y al responsable de IT
      └── Diagnóstico con el historial de refrescos y los logs del gateway
            └── Resolución y refresco manual para que los datos estén disponibles
                antes de las reuniones de negocio
```

Este pipeline elimina completamente la tarea manual de "exportar datos, abrir Power BI Desktop, refrescar, guardar y volver a publicar" que el equipo de analytics hacía antes de configurar el gateway.

## 13. Lo que el gateway ha hecho por debajo

El gateway no es un servidor de datos: es un proceso de relay. Cuando Power BI Service lanza un refresco programado a las 06:00, envía una solicitud cifrada a través de Azure Service Bus hacia la conexión saliente que el gateway mantiene abierta permanentemente. El gateway recibe esa solicitud, la descifra usando la recovery key registrada en el momento de la instalación, y ejecuta localmente la consulta M del modelo semántico contra `\\servidor\datos\reservas.csv`.

El flujo completo de un refresco es este: el motor de Power BI Service serializa el pipeline M del modelo semántico y lo envía al gateway. El gateway ejecuta ese pipeline en su propio proceso (usando el mismo motor de Power Query que hay en Desktop), lee los datos del origen local, aplica todas las transformaciones M, y devuelve los datos comprimidos al servicio por la misma conexión HTTPS saliente. El servicio los recibe y los carga en el motor VertiPaq del modelo semántico, sustituyendo la copia anterior.

Las **credenciales del origen de datos** no viajan en el `.pbix` ni en el pipeline M enviado al gateway. Se almacenan cifradas en el servicio y se envían al gateway en cada refresco junto con la solicitud de datos. El cifrado usa la clave pública del gateway; solo el gateway puede descifrarlas con su clave privada. Esto significa que ni Microsoft ni nadie que intercepte el tráfico puede leer las credenciales del origen de datos.

La diferencia entre el gateway estándar y el Personal Gateway no es solo de escala: el Personal Gateway ejecuta en la sesión del usuario de Windows, lo que significa que si el PC se bloquea, se apaga o el usuario cierra sesión, el gateway se detiene y el refresco falla. El gateway estándar corre como servicio de Windows (con cuenta `svc-powerbi`), arranca con el sistema operativo y es independiente de cualquier sesión de usuario.

## 14. Errores comunes

**"Unable to connect to the data source" al validar la fuente de datos en el gateway.**
El servidor donde está instalado el gateway no puede acceder a la ruta `\\servidor\datos\reservas.csv`. Verificar: (1) que el servicio del gateway corre con la cuenta `svc-powerbi`, (2) que esa cuenta tiene permisos de lectura en la carpeta compartida, (3) que el servidor puede resolver el nombre `\\servidor\` por DNS.

**"The gateway is offline" en el panel de Manage gateways.**
El servicio de Windows del gateway está parado en el servidor. Conectarse a `SERVIDOR-BI-01` y abrir el Administrador de Servicios de Windows (`services.msc`). Buscar el servicio "On-premises data gateway service" y verificar que está en estado "Running". Si está parado, iniciarlo manualmente e investigar el log de eventos para encontrar la causa.

**"Refresh failed: The credentials provided for the source are invalid."**
Las credenciales de la fuente de datos han caducado o la contraseña de `svc-powerbi` ha cambiado. En **Manage gateways > fuente de datos > Edit credentials**, introducir las credenciales actualizadas.

**"Scheduled refresh is disabled" aparece en el historial aunque el toggle esté activo.**
Esto ocurre cuando el propietario del modelo semántico ha cambiado (por ejemplo, si la cuenta que publicó el modelo ya no tiene licencia Pro activa). El nuevo propietario tiene que entrar en Settings y guardar la configuración del refresco para reactivarlo.

**El refresco tarda más de 30 minutos y a veces se cancela.**
Con archivos CSV grandes sin query folding, toda la carga ocurre en memoria del gateway. Soluciones: (1) Migrar el CSV a una base de datos SQL Server que soporte query folding. (2) Activar la actualización incremental si el origen la soporta. (3) Filtrar los datos en Power Query para reducir el volumen cargado.

**"Gateway version is out of date."**
El gateway instalado tiene más de 6 meses de antigüedad. Descargar la última versión desde el panel de Manage gateways y ejecutar el instalador en el servidor. El instalador detecta la instalación existente y la actualiza sin perder la configuración.

**El informe muestra datos del día anterior a las 10:00, cuando el refresco debería haber terminado a las 06:15.**
El refresco se ha ejecutado pero el modelo semántico tiene caché. Abrir el informe en el servicio y hacer clic en el botón de refresco manual del informe (no del modelo semántico). Si el problema persiste, verificar en el historial de refrescos que el refresco de las 06:00 terminó con éxito.

## 15. Ampliación opcional

### Extra 1: Gateway con múltiples orígenes de datos

En una organización real, el gateway no gestiona un solo origen sino docenas. HotelesMediterraneum podría en el futuro tener:
- `reservas.csv` (tipo File, ya configurado)
- SQL Server de contabilidad (`SQLSERVER-CONT\RevenueDB`)
- Base de datos de RRHH en Oracle local
- Varios archivos Excel compartidos en carpetas de red

Cada origen de datos se añade como una fuente independiente en el mismo gateway. El gateway actúa de broker centralizado para todos ellos. Los modelos semánticos en el servicio se vinculan cada uno a su fuente correspondiente.

Para añadir el SQL Server de contabilidad: **Manage gateways > + Add data source**, seleccionar el tipo `SQL Server`, introducir el servidor, la base de datos, y las credenciales. El proceso es idéntico al de File, solo cambia el tipo y los campos de conexión.

### Extra 2: PowerShell para gestión masiva del gateway

La API REST de Power BI permite gestionar gateways y fuentes de datos de forma programática. Para organizaciones con muchos gateways, esto es imprescindible.

Ejemplo: listar todos los gateways del tenant con PowerShell y el módulo MicrosoftPowerBIMgmt:

```powershell
Install-Module -Name MicrosoftPowerBIMgmt -Force
Connect-PowerBIServiceAccount

# Listar todos los gateways
$gateways = Invoke-PowerBIRestMethod -Url "gateways" -Method Get | ConvertFrom-Json
$gateways.value | Select-Object id, name, gatewayStatus, gatewayVersion

# Listar las fuentes de datos de un gateway concreto
$gatewayId = ($gateways.value | Where-Object name -eq "GW-HotelesMediterraneum-01").id
Invoke-PowerBIRestMethod -Url "gateways/$gatewayId/datasources" -Method Get | ConvertFrom-Json
```

Esto es útil para auditorías periódicas: verificar que todos los gateways están en la última versión, que no hay fuentes de datos huérfanas (sin modelo semántico que las use), o que las credenciales se han renovado recientemente.
